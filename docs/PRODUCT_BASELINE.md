# 球搭子｜产品规则基线（Current Product Baseline）

> 状态：当前 H5 MVP 产品真源之一。用于吸收早期 PRD V5 之后已经明确的产品决策；原则稳定，细节可随用户明确讨论继续增量更新。

## 1. 产品目标

球搭子是面向真实网球爱好者的移动端赛事工具：让朋友可以先组织比赛、报名组队、编排、记分、排名晋级和保存比赛记录，并逐步形成长期球友关系和个人打球档案。

P0 必须是真实公网、多用户共享同一份云端赛事数据的 H5，不是静态 Demo、单机 IndexedDB Demo 或微信小程序。

## 2. 核心实体不可混淆

### Profile / User
真实使用产品的人和登录身份。负责昵称、头像、城市等用户资料。

### Player
比赛世界里的长期参赛身份。Player 可以先于真实用户存在；赛事历史、Entry、Match 关联 Player，而不是直接依赖登录账号。

### Connection
两个真实 Profile 之间的球搭子关系。只有双方都是真实用户后才存在 Connection。

### Event / Entry / Match
- Event：赛事。
- Entry：报名/参赛单元。单打一个 Entry 一人；双打一个 Entry 两人。
- Match：两个 Entry 之间的一场比赛。

禁止用姓名/昵称作为实体关联键；禁止把 User/Profile 与 Player 合并。

## 3. “先比赛，人后加入”原则

用户可以为尚未使用球搭子的朋友创建临时 Player，并用于报名、组队、比赛和记录战绩。历史数据必须跟随 Player 持久化。

临时球搭子以后成为真实用户时，通过明确邀请流程关联其既有历史，并建立 Connection；历史不能因为加入系统而丢失或复制成两份。

### 临时球搭子档案展示策略

后台持续保存临时 Player 的比赛历史和可计算档案数据，包括参赛、胜负、赛事、对手/搭档等。

前台对创建者只展示管理所需的基础信息和“已有历史记录/加入后可解锁”的提示，不展开完整战绩明细、胜率、具体历史比赛等价值内容。完整档案应在本人加入并完成历史关联后成为其长期个人资产，以此形成自然的用户转化动力。

创建者仍可编辑临时球搭子的基础资料、继续用于报名和比赛，并发起“邀请 TA 加入球搭子”。

## 4. 球搭子关系与邀请

“球搭子们”分为：

- 我的球搭子：已建立 Connection 的真实用户。
- 临时球搭子：由当前用户管理、尚未关联真实用户的 Player。

不要使用“正式球搭子”作为产品术语。

### 普通球搭子邀请

每次邀请应生成独立、可追踪的邀请记录/token。对方打开并完成必要身份流程后自动建立 Connection，不增加无意义的二次确认。

### 临时球搭子加入邀请

用于邀请某个临时 Player 对应的人加入，并确认/关联此前的比赛历史。该流程与普通球搭子邀请语义不同，前台不要出现“claim / merge Player / 数据迁移”等内部术语。

### 球搭子邀请记录

“我的 → 球搭子邀请记录”统一展示两类球搭子邀请的生命周期：普通球搭子邀请 + 临时球搭子加入/历史关联邀请。状态应可理解，例如等待加入、已加入/已关联、已取消、已失效。

赛事邀请不混入这里；赛事邀请属于“我的赛事”。

## 5. 赛事信息架构

### 赛事大厅
职责只有发现、筛选、查看和进入报名。大厅不承担创建赛事职责。

无公开赛事时显示发现型空状态，例如“暂时没有公开赛事”，可引导“去我的赛事”，但不直接放“创建赛事”主按钮。

赛事卡片应优先帮助用户快速判断是否值得进入，至少包含：

- 赛事名称和状态；
- 组织者头像/昵称/“组织者”；
- 城市；
- 赛事级别；
- 单/双打、赛制/计分概要；
- 日期时间；
- 场地；
- 已报名/名额；
- 费用概要。

城市是 Event 的独立必填字段，不能从 venue 字符串猜测；创建赛事时必须填写城市，并直接显示在赛事卡片上。

赛事等级与个人档案保持同一、适合大众业余球友的六档体系：2.0及以下 / 2.5 / 3.0 / 3.5 / 4.0 / 4.5及以上。内部存储值可使用 `≤2.0` / `≥4.5`，用户界面展示人话标签。

### 赛事可见范围

创建赛事时必须在“公开 / 私有”之间明确选择：

- **公开赛事**：所有用户都可以在赛事大厅发现和查看，允许正常公开报名。
- **私有赛事**：不出现在公开赛事大厅；只有组织者、被该赛事明确邀请的用户，以及已实际报名进入该赛事的用户可以查看。仅知道赛事 URL 不能绕过权限查看私有赛事。

私有赛事的限制必须由后端读取权限保证，不能只靠前端隐藏卡片。旧的“仅链接可见”模式不再作为产品规则。

### 我的赛事
分为：

- 我创建的：创建、管理、编排、记分等组织者工作。
- 我参与的：只展示当前用户已经真正完成报名并存在有效 Entry 的赛事。

接受赛事邀请 ≠ 完成报名。普通赛事邀请接受后仍需完成报名；双打搭档接受组队邀请也不自动等于最终 Entry，发起方仍需完成报名。

### 赛事邀请的决策信息

赛事邀请页是“是否参加/是否组队”的决策页面，不应只显示赛事名。邀请卡至少应提供日期、城市 + 场地、赛事级别、单/双打或“双打组队”类型；待回应邀请优先于已经结束的历史邀请展示。

动作层级必须清楚：接受为 Primary Action，暂不参加为 Secondary Action，查看赛事是低强调详情入口，不能三个大按钮并列争抢注意力。

## 6. 报名与组织者代报名

真实 Connection：组织者可邀请参赛，由对方自行完成报名。

临时球搭子：组织者可在获得现实授权/同意的前提下代报名。

双打必须以一个 Entry 表示一支队伍，不能把两名搭档拆成两个独立报名人进入签表。

## 7. 我的打球档案、我的战绩、我的赛事

三者职责严格区分：

- 我的打球档案：长期身份、水平、城市、单双打偏好、常打时间等。
- 我的战绩：已经完成的比赛结果与长期表现。
- 我的赛事：我组织或实际报名参与的赛事及其进行状态。

昵称/头像编辑是身份资料动作，不与水平/偏好等打球档案编辑混成重复页面。

## 8. 测试身份与未来正式身份

当前受控测试阶段可暂时使用昵称选择既有测试身份；该方案明确不安全，不作为正式登录设计。公开 ID 当前不需要展示给测试用户。

正式产品后续应接入可靠身份体系（如微信），头像可由用户选择使用微信头像，但属于 optional；不能把昵称当正式唯一登录凭证。

## 9. 数据刷新与性能

球搭子不是高频金融/即时聊天业务。稳定数据禁止默认每 10–15 秒轮询。

默认策略：

- 首次加载；
- 已有缓存立即展示；
- stale-while-revalidate；
- 页面重新激活时仅在 stale 后后台刷新；
- 手动刷新；
- mutation 后精准失效相关缓存。

只有进行中的赛事详情、实时记分、多人同时变化的比分/名单等场景可保留较短刷新；未来可评估 Supabase Realtime。

## 10. 产品语言

用户看到的是赛事、球搭子、报名、邀请、档案、战绩和历史记录，不是数据库模型。

禁止前台直接出现：RPC、RLS、JWT、Profile ID、Player merge、claim、迁移、数据库错误等技术语言。

错误信息应说明用户能理解的状态和下一步，例如网络较慢、登录状态失效、邀请已失效、名单已锁定等。

## 11. 不变的赛事规则底线

- 创建赛事时不自动生成对阵。
- 名单锁定、编排、比分、晋级必须遵守状态机。
- 不允许非法比分保存。
- 已影响下游比赛的上游结果不能无保护直接覆盖。
- 排名不依赖 PointLog 才能计算。
- 权限不能只靠隐藏前端按钮。
- 核心数据必须云端持久化并支持多人共享。
- 不擅自扩展支付、俱乐部、多管理员、聊天等未确认范围。
