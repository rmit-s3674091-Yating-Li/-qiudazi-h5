# 球搭子｜产品规则基线（Current Product Baseline）

> 状态：当前 H5 MVP 产品真源之一。用于吸收早期 PRD V5 之后已经明确的产品决策；原则稳定，细节可随用户明确讨论继续增量更新。

## 1. 产品目标

球搭子是面向真实网球爱好者的移动端赛事工具：让朋友可以先组织比赛、报名组队、编排、记分、排名晋级和保存比赛记录，并逐步形成长期球友关系和个人打球档案。

P0 必须是真实公网、多用户共享同一份云端赛事数据的 H5，不是静态 Demo、单机 IndexedDB Demo 或微信小程序。

## 2. 核心实体不可混淆

### Profile / User
真实使用产品的人和登录身份。负责昵称、头像、城市等用户资料。

### Player
比赛世界里的长期参赛身份。Player 可以先于真实用户存在；赛事历史、Entry、Match 关联 Player，而不是直接依赖登录账号。

### Connection
两个真实 Profile 之间的球搭子关系。只有双方都是真实用户后才存在 Connection。

### Event / Entry / Match
- Event：赛事。
- Entry：报名/参赛单元。单打一个 Entry 一人；双打一个 Entry 两人。
- Match：两个 Entry 之间的一场比赛。

禁止用姓名/昵称作为实体关联键；禁止把 User/Profile 与 Player 合并。

## 3. “先比赛，人后加入”原则

用户可以为尚未使用球搭子的朋友创建临时 Player，并用于报名、组队、比赛和记录战绩。历史数据必须跟随 Player 持久化。

临时球搭子以后成为真实用户时，通过明确邀请流程关联其既有历史，并建立 Connection；历史不能因为加入系统而丢失或复制成两份。

### 临时球搭子档案展示策略

后台持续保存临时 Player 的比赛历史和可计算档案数据，包括参赛、胜负、赛事、对手/搭档等。

前台对创建者只展示管理所需的基础信息和“已有历史记录/加入后可解锁”的提示，不展开完整战绩明细、胜率、具体历史比赛等价值内容。完整档案应在本人加入并完成历史关联后成为其长期个人资产。

创建者仍可编辑临时球搭子的基础资料、继续用于报名和比赛，并发起“邀请 TA 加入球搭子”。

## 4. 球搭子关系与邀请

“球搭子们”分为：我的球搭子（accepted Connection 的真实用户）和临时球搭子（由当前用户管理、尚未关联真实用户的 Player）。不要使用“正式球搭子”作为产品术语。

普通球搭子邀请每次生成独立可追踪邀请记录/token；对方完成必要身份流程后自动建立 Connection，不增加无意义的二次确认。临时球搭子加入邀请用于确认/关联此前比赛历史，前台不出现 claim / merge Player / 数据迁移等内部术语。

“我的 → 球搭子邀请记录”展示普通球搭子邀请 + 临时球搭子加入/历史关联邀请；赛事邀请归“我的赛事”。

## 5. 赛事信息架构

### 赛事大厅
职责只有发现、筛选、查看和进入报名，不承担创建赛事。大厅可以发现公开赛事和经过隐私脱敏的私有赛事。

城市是 Event 独立必填字段，不能从 venue 猜测。

### 参赛建议级别
赛事用户侧不再使用单一“赛事级别”，统一为“参赛建议级别”区间。六档为：2.0及以下 / 2.5 / 3.0 / 3.5 / 4.0 / 4.5及以上；内部可使用 `≤2.0` / `≥4.5`。创建/编辑允许最低、最高、单边开放或不限，最低不得高于最高。建议级别仅用于发现和匹配，不是硬报名资格。

展示规则：不限；单一中间档显示“建议 3.0”；仅最低显示“建议 3.5及以上”；仅最高显示“建议 3.0及以下”；区间显示“建议 2.5–3.5”。阈值档按六档有序模型处理，不做字符串字典序比较。公开卡、完整详情、邀请信息可展示；私有脱敏预览也允许展示建议级别。旧单值 level 仅作为兼容迁移来源，不再作为用户侧筛选/概念。

### 赛事可见范围
- 公开赛事：所有用户可发现、查看完整公开详情并正常公开报名。
- 私有赛事：大厅只展示脱敏预览。未获权限用户可看到赛事名称、城市、参赛建议级别、单/双打、赛制、状态和私有标识；不得看到组织者、参赛人、报名/候补人数、具体日期时间、具体场地、费用或报名截止时间。
- 私有赛事大厅预览不等于获得详情权限或报名资格。未获权限用户点击后只能看到受限预览，不得通过已知赛事 ID / URL 绕过后端权限。
- 组织者、明确收到该赛事邀请的用户，以及已实际报名进入该赛事的用户可解锁完整详情。

稳定原则：**大厅可发现 ≠ 获得赛事详情权限 ≠ 获得报名资格。**

### 我的赛事
分为“我创建的”和“我参与的”。“我参与的”以当前真实用户对应 Player 是否属于有效 Entry 为准；双打 Entry 的两名真实搭档都属于实际参与者，不能只用 `signup_user_id` 判断。

接受赛事邀请 ≠ 完成报名。普通赛事邀请接受后仍需完成报名；双打搭档接受组队邀请也不自动等于最终 Entry。

### 组织者身份
赛事快照返回的服务端 `viewer_role` 是赛事页面判断 owner / participant / invited / viewer 的权威依据。身份敏感 UI 不得仅依赖可能过期的本地 Profile ID 比较；前端显示管理入口与服务端权限必须保持一致，服务端仍是最终授权边界。

### 赛事邀请与分享
- 公开赛事鼓励传播。组织者或已经实际报名的参与者可邀请自己的 Connection 参赛；普通浏览者可以分享公开链接但不能发正式参赛邀请。
- 双打可明确发出“邀请 TA 和我组队”；接受只表示搭档意向，仍需完成双打 Entry。
- 私有赛事普通参赛邀请由组织者控制。私有双打中已有合法访问/参赛资格的用户可邀请自己的球搭子组队，搭档只获得完成组队所需访问资格。
- 未获权限用户分享私有赛事只能传播脱敏预览，不授予完整详情或报名资格。

## 6. 比赛时间、报名与名单锁定

比赛日期和开赛时间为创建赛事 P0 必填。最晚报名时间默认开赛前 2 小时；组织者可以设置得更早，但不能晚于开赛前 2 小时。修改比赛日期/开赛时间后，如果原截止时间超过新边界，系统自动收紧到新的合法最晚值，并必须明确提示组织者已自动调整。

报名截止是服务端权限边界。到达截止点后，单打/双打报名、组织者代临时球搭子报名、双打最终 Entry 提交、普通邀请接受、双打邀请接受、普通退赛等所有改变名单的普通路径必须被服务端拒绝。旧页面、分享深链、提前打开的页面和直接 RPC 调用均不得绕过。组织者可以在截止前提前锁定。

截止后进入“报名截止 / 名单锁定，等待编排或开赛”，不等于比赛开始。即使后台物理状态同步任务尚未运行，服务端写入判断和列表有效状态也必须立即按截止时间视为已锁定。报名截止但人数不足时，应明确提示“报名已截止，但当前人数不足以编排”。

真实 Connection 由本人完成报名；临时球搭子可由组织者在现实授权/同意前提下代报名。双打必须以一个 Entry 表示一队。

### 报名截止展示
公开/完整赛事卡使用已加载 deadline + 本地时钟显示，不为倒计时增加网络轮询：>24小时显示具体截止日期时间；1–24小时显示约 N 小时；不足1小时显示“报名即将截止”；截止后显示“报名已截止”；提前人工锁定显示“报名已结束”。最终可报名性始终由服务器决定。私有未授权预览不得展示 deadline。

## 7. 设置、隐私与语言

“我的 → 设置与隐私”是真实设置页。

个人档案字段按字段控制球搭子浏览可见性：头像、水平级别、常打城市、约球时间、单双打偏好。昵称及赛事共同事实不受该开关影响；赛事名单、比分、赛果等共同事实不得被个人档案隐私开关改写。档案可见性必须由服务端裁剪执行。

邀请隐私有两个独立开关，默认开启：允许赛事邀请；允许双打组队邀请。必须由服务端邀请 RPC 执行，不能只隐藏按钮。

H5 MVP 支持简体中文 / English。语言偏好本地持久化，使用统一轻量 i18n 层，不建立复杂国际化后端。进入英文可用验收时，核心流程必须完整覆盖，不能出现半翻译；默认中文也不得残留无意义装饰英文。新增核心用户可见文案原则上进入统一语言资源或共享语言 helper，业务逻辑不得依赖某一种语言的展示文案。

## 8. 我的打球档案、我的战绩、我的赛事
三者职责严格区分：我的打球档案是长期身份与偏好；我的战绩是已完成比赛结果与长期表现；我的赛事是我组织或实际报名参与的赛事。

## 9. 测试身份与未来正式身份
当前受控测试阶段可暂时使用昵称选择既有测试身份；该方案明确不安全，不作为正式登录设计。公开 ID 当前不需要展示。正式产品后续应接入可靠身份体系（如微信），头像可 optional 使用微信头像，不能把昵称当正式唯一登录凭证。

## 10. 数据刷新与性能
稳定数据禁止默认每 10–15 秒轮询。默认使用缓存、stale-while-revalidate、页面重新激活后的按需刷新、手动刷新和 mutation 后精准失效。只有进行中的赛事详情、实时记分等确有多人变化的场景可短刷新。

## 11. 产品语言与技术边界
用户看到的是赛事、球搭子、报名、邀请、档案、战绩和历史记录，不是数据库模型。UI 禁止直接出现 RPC、RLS、JWT、Profile ID、Player merge、claim、迁移、数据库错误等技术语言。错误信息应说明用户能理解的状态和下一步。

## 12. 不变的赛事规则底线
- 创建赛事时不自动生成对阵。
- 名单锁定、编排、比分、晋级必须遵守状态机。
- 不允许非法比分保存。
- 已影响下游比赛的上游结果不能无保护直接覆盖。
- 排名不依赖 PointLog 才能计算。
- 权限不能只靠隐藏前端按钮。
- 核心数据必须云端持久化并支持多人共享。
- 不擅自扩展支付、俱乐部、多管理员、聊天等未确认范围。
