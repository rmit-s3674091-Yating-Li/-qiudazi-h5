# 球搭子｜视觉设计基线（Canonical UI Baseline）

> **状态：长期有效 / 前端设计强约束**
>
> 本文件是「球搭子」H5 后续页面、组件与交互视觉实现的默认设计依据。新增页面、重构页面、AI/Codex 生成前端代码前，应同时阅读 `PRODUCT_BASELINE.md`、`INTERACTION_BASELINE.md`，并结合当前已有页面与 `src/styles.css` 判断实现方式。
>
> 优先级：**功能与业务规则正确 > 产品/交互基线 > 本视觉基线 > 当前已验证的组件/页面模式 > 早期视觉 Demo。**
>
> 视觉 Demo 只提供方向，不要求机械复刻。若 Demo 与当前产品结构、可用性或本文件冲突，以当前产品基线为准。

## 1. 产品视觉定位

「球搭子」不是专业赛事管理后台，也不是 ATP/WTA 数据终端，更不是泛社交 App。

它是一款给真实网球爱好者使用的、**轻松但认真、好看但不过度装饰、可以真正组织和记录一场比赛的移动端赛事工具**。

核心气质：**轻松 / 现代 / 克制 / 明亮 / 低饱和 / 有网球感 / 有少量编辑设计感 / 生活方式感 / 移动端优先 / 信息清晰。**

## 2. 当前产品的设计原则

### 2.1 功能先于装饰
页面首先回答：我在哪里、最重要的信息是什么、下一步做什么。视觉不能降低三者清晰度。

### 2.2 信息密度
信息密度高于纯生活方式/社交 App，但明显低于专业赛事后台。复杂业务通过层级、分区、渐进展示解决，不一次塞入所有字段。

### 2.3 一页一个主要动作
一个页面原则上只有一个最明显的 Primary Action。若两个一级页面都出现同一个 Primary Action，优先检查页面职责是否重复，而不是继续增加快捷入口。

### 2.4 人优先于账号，赛事优先于字段
球搭子页强调“人”；赛事大厅强调“比赛”；战绩页强调“结果”。不要把数据库结构直接翻译成 UI。

### 2.5 展示优先，编辑按需进入
个人档案、赛事信息默认优先可读，编辑通过明确入口进入。

### 2.6 卡片代表实体
点击整张实体卡片默认进入该实体详情：赛事→赛事详情，人→人的档案/管理详情。编辑、邀请、删除、报名等必须是明确动作，不能让不同卡片的“整卡点击”有时代表详情、有时偷偷代表编辑。

### 2.7 空状态不改变页面职责
空状态可以引导下一步，但不能为了“有按钮”把本不属于该页面的主功能重新塞回来。文案必须符合真实状态机，不以友好为由描述错误业务状态。

## 3. 色彩体系

保留暖米白 + 鼠尾草绿 + 灰蓝 + 红土橙方向。

- 页面基础色：象牙白、米白、极浅暖灰、极浅蓝灰，避免整页生硬纯白。
- 硬地蓝/灰蓝：主按钮、主要选中态、核心信息强调，保持低饱和。
- 鼠尾草绿/橄榄绿：成功、胜场、场地氛围、轻量标签。
- 红土橙：适度提醒、赛事个性、重点数据，避免鲜艳橙。
- 网球黄绿色：只作 LIVE/当前比赛/关键状态高光，禁止大面积使用。
- 文字：深炭灰、暖黑、深灰蓝；层级靠字号、字重、灰度、空间共同建立。

优先复用 `src/styles.css` 已有 CSS variables，避免页面各自发明颜色。

## 4. 排版与空间

- Mobile first，默认单列。
- 稳定左右边距与安全区。
- 大标题清楚但不做海报式超大标题。
- 模块主要靠留白和标题分区，不依赖每块都套卡片。
- 触摸目标建议至少约 44px。
- 长页面自然纵向滚动；签表等复杂结构允许局部横向滚动。
- 不为“多放内容”压缩字体和间距。

## 5. 卡片与容器

卡片承载真正属于同一语义单元的信息，不是默认布局工具。推荐适中圆角、浅背景、轻边框、极轻阴影、充足内边距。

禁止厚重投影、强悬浮、高对比描边、卡片套卡片、每字段一张卡、大量玻璃拟态。

## 6. 网球图形语言

持续使用抽象、几何、克制的球场线、圆/圆弧、轨迹/落点、对阵连接线、简化球体。避免大量真实球拍、球员剪影、体育贴纸和无意义插图。

## 7. 图标

简洁、线性、圆润、统一线宽；优先统一图标库。禁止把 Emoji 当正式功能图标，不混用线性/实心/拟物/3D 风格。关键操作仍应有文字。

## 8. 按钮与操作层级

主按钮明显但不厚重；大触摸区；短而明确的动词。次级操作降级。多个同级动作优先 Action Sheet / Bottom Sheet。危险操作需明确文案和必要确认。

## 9. Bottom Sheet / 弹层

Bottom Sheet 是辅助操作容器，不是第二个完整页面。标题独立、动作清楚、图标/标题/说明/箭头统一对齐；同一 Sheet 不塞复杂表单。

## 10. 核心页面专项规则

### 10.1 赛事大厅
不像后台列表，只负责发现赛事。赛事卡优先回答：什么比赛、谁组织、什么水平、哪个城市、什么时候、什么赛制、多少人、当前状态。城市和级别是决策信息，不能为了“极简”删掉；无数据时不能猜。

大厅空状态不直接创建赛事；创建归“我的赛事 → 我创建的”。

### 10.2 我的赛事
强调“我创建/实际报名参加的赛事”和当前进度，不复制大厅全部筛选逻辑。“我参与的”以有效 Entry 为准，不能把仅接受邀请描述成已经参加。

### 10.3 球搭子们
强调真实用户关系：头像、昵称、关系与下一步约球可能性。

**球搭子 ≠ 所有 Player。** “我的球搭子”与“临时球搭子”分开呈现，不使用“正式球搭子”。

临时球搭子是次级管理对象：后台可积累完整历史，但创建者前台不展开完整战绩价值；展示基础管理信息、已有记录提示和邀请加入入口，以“加入后解锁自己的完整档案”形成自然转化。

### 10.4 我的 / 我的打球档案
“我的”是个人入口，不做 Dashboard。打球档案展示优先，重点突出水平、城市、约球时间、单双打偏好。头像昵称编辑与打球档案编辑在标题上明确区分。

### 10.5 我的战绩
与“我的赛事”严格区分。战绩回答“我打得怎么样”，赛事回答“我参加/组织了什么”。比分以当前用户视角显示，不做专业数据终端。

### 10.6 报名 / 选择参赛者
核心是“选择这次谁参赛”，不是管理球员数据库。本人、真实球搭子、临时球搭子在视觉和业务含义上清楚区分。双打围绕一个两人 Entry 设计。

### 10.7 实时计分
关键词：明亮、快速、户外可读、大点击区域。比分最醒目，双方易区分，Undo 易找但不易误触。禁止黑底电竞直播和 ATP/WTA 数据终端风格。

### 10.8 排名
兼顾荣誉感和可读性。前三名适度强化，其他统一。不要 Excel 化、金银铜渐变、3D 奖杯和电竞排行榜视觉。

### 10.9 淘汰签表
首先是信息图：对阵、晋级路径、当前/已完成比赛清楚。移动端允许横向滑动、分轮或卡片式 bracket，禁止缩小到不可读。

## 11. 空状态

空状态不能只是“暂无数据”。推荐：轻量网球几何元素 + 人话标题 + 一句真实解释 + 一个符合当前页面职责的下一步动作。

空状态文案必须与状态机一致。例如“接受赛事邀请”不能被写成“已经报名”。

## 12. Loading / Error / Empty / Success

统一反馈模式。已有缓存时优先保留内容并后台更新，不因为每次切 Tab 都清空成 Loading。稳定页面不靠频繁轮询制造“实时感”。

错误提示必须是用户语言，不直接显示数据库、JWT、RPC、SQL 等底层信息。

## 13. 明确禁止

- 电竞化：黑色主背景、霓虹蓝紫、HUD、发光边框、直播数据大屏。
- 企业后台化：密集表格、大量筛选器、多层菜单、ERP Dashboard、数据库字段直出。
- 儿童运动 App 化：彩虹配色、大量卡通、Emoji 堆叠、过度可爱。
- 专业赛事系统照搬：不复制 ATP/WTA/ITF/裁判终端/电视转播 UI。
- AI 默认审美：无业务意义紫蓝渐变、巨大 Hero、每页四宫格、玻璃拟态、发光球体、装饰性 Dashboard。
- 为了“入口方便”复制同一主功能到多个一级页面。
- 为了视觉完整伪造数据库不存在的城市、级别、战绩或关系状态。

## 14. 前端实现约束

每次新增或明显重构页面前：

1. 确认业务对象和唯一主要用户任务；
2. 阅读 `PRODUCT_BASELINE.md`、`INTERACTION_BASELINE.md` 和本文件；
3. 检查已有相近页面和 `src/styles.css`，优先复用；
4. 明确页面唯一 Primary Action；
5. 确认整卡点击语义与同类实体一致；
6. 确认空状态没有越权承担别的页面职责；
7. 不新增与现有语义重复的组件/class；
8. 重构完成后删除已被替代的整套旧页面/旧术语；
9. 大改部署前对照三份 baseline 做原则偏移审计。

局部需求不得顺手重写全局视觉和交互原则。确需改变全局原则时，先明确产品决策，再更新 baseline。
