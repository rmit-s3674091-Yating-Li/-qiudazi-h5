# 球搭子｜视觉设计基线（Canonical UI Baseline）

> **状态：长期有效 / 前端设计强约束**
>
> 本文件是「球搭子」H5 后续页面、组件与交互视觉实现的默认设计依据。新增页面、重构页面、AI/Codex 生成前端代码前，应先阅读本文件，并结合当前已有页面与 `src/styles.css` 判断实现方式。
>
> 优先级：**功能与业务规则正确 > 本视觉基线 > 当前已验证的组件/页面模式 > 早期视觉 Demo。**
>
> 视觉 Demo 只提供方向，不要求机械复刻。若 Demo 与当前产品结构、可用性或本文件冲突，以当前产品与本文件为准。

## 1. 产品视觉定位

「球搭子」不是专业赛事管理后台，也不是 ATP/WTA 数据终端，更不是泛社交 App。

它是一款给真实网球爱好者使用的、**轻松但认真、好看但不过度装饰、可以真正组织和记录一场比赛的移动端赛事工具**。

核心气质：

**轻松 / 现代 / 克制 / 明亮 / 低饱和 / 有网球感 / 有少量编辑设计感 / 生活方式感 / 移动端优先 / 信息清晰。**

用户首先应该感受到：

> 这是朋友们约球、组织比赛、记比分、看战绩、保持球友联系的产品。

而不是：

> 专业裁判系统、电竞比分系统、企业赛事后台或数据库管理工具。

## 2. 当前产品的设计原则

### 2.1 功能先于装饰

页面首先回答三个问题：

1. 我现在在哪里？
2. 当前最重要的信息是什么？
3. 下一步最应该做什么？

任何视觉设计都不能降低这三件事的清晰度。

### 2.2 信息密度

信息密度应 **高于纯生活方式/社交 App，但明显低于专业赛事后台**。

复杂业务通过层级、分区、渐进展示解决，而不是一次性塞入所有字段。

### 2.3 一页一个主要动作

一个页面原则上只有一个最明显的 Primary Action，例如：创建赛事、立即报名、锁定名单、开始比赛、提交比分、保存档案。

其他操作使用次级按钮、文字按钮、图标按钮或 Bottom Sheet。

### 2.4 人优先于账号，赛事优先于字段

球搭子页强调“人”；赛事大厅强调“比赛”；战绩页强调“结果”。不要把数据库结构直接翻译成 UI。

### 2.5 展示优先，编辑按需进入

个人档案、赛事信息等内容页默认优先呈现可阅读的信息，而不是打开页面就出现大量输入框。编辑应通过明确入口进入。

## 3. 色彩体系

现有产品的暖米白 + 鼠尾草绿 + 灰蓝 + 红土橙方向继续保留。

### 页面基础色

优先：象牙白、米白、极浅暖灰、极浅蓝灰。避免整页生硬纯白。

### 硬地蓝 / 灰蓝

用于主按钮、主要选中态、核心信息强调。保持低饱和，禁止互联网科技蓝式高饱和。

### 鼠尾草绿 / 橄榄绿

用于成功、胜场、场地氛围、轻量标签与自然系装饰。

### 红土橙

用于适度提醒、赛事个性、重点数据或局部卡片装饰。避免鲜艳橙色。

### 网球黄绿色

只作为高辨识度高光：LIVE、当前比赛、当前选手、关键状态点。**禁止大面积使用。**

### 文字

正文优先深炭灰、暖黑、深灰蓝。层级通过 **字号 + 字重 + 灰度 + 空间关系** 共同建立，不靠大量彩色文字。

> 实现时优先复用 `src/styles.css` 已有 CSS variables；新增颜色应先判断是否可以由现有 token 表达，避免页面各自发明颜色。

## 4. 排版与空间

- Mobile first，默认单列。
- 内容区保持稳定左右边距与安全区。
- 大标题清楚，但不做海报式超大标题。
- 模块之间主要依靠留白和标题分区，不依赖每块都套卡片。
- 触摸目标建议至少约 44px。
- 长页面保持自然纵向滚动；签表等复杂结构允许局部横向滚动。
- 不为了“多放内容”而压缩字体和间距。

信息层级：

- 一级：页面标题 / 赛事名称。
- 二级：模块标题 / 对阵双方 / 关键排名。
- 三级：时间、场地、规则、状态辅助信息。
- 数据层：比分、排名、胜负等可适度放大，但禁止数据大屏化。

## 5. 卡片与容器

卡片用于承载真正属于同一语义单元的信息，而不是默认布局工具。

推荐：适中圆角、浅背景、轻边框、极轻阴影、充足内边距。

禁止：

- 厚重投影；
- 强悬浮；
- 高对比描边；
- 卡片套卡片套卡片；
- 每个字段一张卡；
- 为了“高级感”大量玻璃拟态。

页面需要有呼吸感。

## 6. 网球图形语言

持续使用抽象、几何、克制的网球视觉元素：

- 球场线与边界；
- 圆、半圆、圆弧；
- 网球轨迹与落点；
- 对阵连接线；
- 简化球体。

这些元素用于建立产品识别，不是素材装饰库。避免大量真实球拍、球员剪影、体育贴纸和无意义插图。

## 7. 图标

图标必须简洁、线性、圆润、统一线宽。优先统一图标库或现有组件。

禁止把 Emoji 当正式功能图标，也不要混用线性、实心、拟物、3D 多套风格。

图标辅助识别，关键操作仍应有文字。

## 8. 按钮与操作层级

主按钮：明显但不厚重；圆角；大触摸区；短而明确的动词文案。

次级操作降级处理。多个同级动作优先用 Action Sheet / Bottom Sheet，而不是在页面堆一排高亮按钮。

危险或不可逆操作不能仅靠颜色区分，应有明确文案和必要确认。

## 9. Bottom Sheet / 弹层

Bottom Sheet 是移动端辅助操作容器，不应变成第二个完整页面。

- 标题独立成行；
- 每个动作形成清晰行项目；
- 主标题和说明上下排列，不横向挤压；
- 图标、标题、说明、箭头保持统一对齐；
- 关闭动作清晰但不抢主操作；
- 同一 Sheet 不塞入复杂表单。

## 10. 核心页面专项规则

### 10.1 赛事大厅

不像后台列表。每张赛事卡优先回答：什么比赛、什么时候、什么赛制、多少人、当前状态、我是否参加。

蓝 / 绿 / 红土橙可以产生轻微赛事个性，但结构保持一致。

### 10.2 我的赛事

强调“我组织/参加的赛事”和当前进度，不复制赛事大厅全部筛选逻辑。避免标题层级重复，例如页面标题下面再出现同义大标题。

### 10.3 球搭子们

强调真实用户关系：头像、昵称、关系与下一步约球可能性。

**球搭子 ≠ 所有 Player。** 临时参赛者必须作为次级管理对象呈现，不能和真实球搭子混成同一列表，也不能伪造等级、战绩等不存在的数据。

### 10.4 我的 / 我的打球档案

“我的”是个人入口，不做 Dashboard。

打球档案采用“展示优先、编辑按需”：头像昵称保持轻量；重点突出水平、常打城市、约球时间、单双打偏好等真实网球信息。没有数据时给出友好的补充入口，不展示虚构默认值。

### 10.5 我的战绩

“我的战绩”与“我的赛事”严格区分。战绩回答“我打得怎么样”，赛事回答“我参加/组织了什么”。

核心数据可用少量统计卡；比分必须以当前用户视角显示；比赛记录保持轻量、可扫读，不做专业数据终端。

### 10.6 报名 / 选择参赛者

页面核心是“选择这次谁参赛”，不是管理球员数据库。

本人、真实球搭子、临时参赛者需要在视觉和业务含义上清楚区分。不要默认把本人锁死为参赛者；单双打应围绕本次 Entry 所需人数设计选择流程。

### 10.7 实时计分

最特殊页面之一。关键词：**明亮、快速、户外可读、大点击区域。**

当前比分必须最醒目，双方易区分，加分区域足够大，Deuce / AD / Game 一眼可见，Undo 易找到但不易误触。禁止黑底电竞直播和 ATP/WTA 数据终端风格。

### 10.8 排名

兼顾荣誉感和可读性。前三名可适度强化，其他保持统一。不要 Excel 表格化，也不要金银铜渐变、3D 奖杯和电竞排行榜视觉。

### 10.9 淘汰签表

首先是信息图：对阵关系、晋级路径、当前/已完成比赛清楚。移动端允许横向滑动、分轮或卡片式 bracket。禁止为了塞完整签表把文字缩到不可读。

## 11. 空状态

空状态不能只是“暂无数据”。

结构建议：轻量网球几何元素 + 人话标题 + 一句解释 + 一个清晰下一步动作。

例如“还没有比赛战绩 / 完成并提交一场比赛后，结果会自动出现在这里 / 查看我的赛事”。

## 12. 状态、反馈与动效

允许：短促的卡片进入、Tab/状态切换、比分变化、晋级变化、Toast、Bottom Sheet。

动效只帮助理解状态变化。禁止为了展示设计能力加入长动画、炫技转场和持续运动装饰。

Loading / Error / Empty / Success 应使用统一反馈模式。

## 13. 明确禁止

### 电竞化
黑色主背景、霓虹蓝紫、HUD、发光边框、直播数据大屏。

### 企业后台化
密集表格、大量筛选器、多层菜单、ERP Dashboard、数据库字段直出。

### 儿童运动 App 化
彩虹配色、大量卡通、Emoji 堆叠、过度可爱。

### 专业赛事系统照搬
不复制 ATP / WTA / ITF / 裁判终端 / 电视转播 UI。

### AI 默认审美
禁止无业务意义的紫蓝渐变、巨大 Hero、每页四宫格卡片、玻璃拟态、发光球体、装饰性数据 Dashboard。不要因为“AI 常这样设计”而偏离球搭子。

## 14. 前端实现约束

每次新增或明显重构页面前：

1. 先确认业务对象和主要用户任务；
2. 阅读本文件；
3. 检查已有相近页面和 `src/styles.css`，优先复用；
4. 明确页面唯一 Primary Action；
5. 不展示数据库中不存在的数据；
6. 不为单页随意创建一套新颜色、圆角、阴影和按钮体系；
7. 新的通用视觉模式应沉淀为共享 class / component / token，而不是复制 CSS；
8. 手机宽度优先检查信息层级、文字换行、触摸区和 Bottom Nav 安全区；
9. 功能正确后再做视觉 polish，不以视觉改造破坏赛事核心链路；
10. 提交前执行下方自检。

## 15. 页面提交前自检

- [ ] 一眼知道这是什么页面吗？
- [ ] 一眼知道下一步最重要操作吗？
- [ ] 是否有不必要的第二/第三个高亮主按钮？
- [ ] 是否出现数据库不存在的假数据？
- [ ] 是否把真实用户、本人 Player、临时 Player 的概念混在一起？
- [ ] 是否为了“专业”增加了过多参数、筛选和表格？
- [ ] 卡片是否过多或存在卡片套卡片？
- [ ] 颜色是否仍属于现有低饱和体系？
- [ ] 是否出现 Emoji、霓虹、玻璃拟态、3D 或后台 Dashboard 倾向？
- [ ] 空状态是否告诉用户下一步怎么做？
- [ ] 375px 左右手机宽度是否仍可读、可点？
- [ ] 页面是否仍然让人觉得是在“和朋友打网球”，而不是“操作赛事软件”？

## 16. 最终判断标准

当没有 Demo 可参考时，按以下顺序判断：

1. 功能流程正确；
2. 用户一眼理解下一步；
3. 移动端操作顺手；
4. 信息真实且层级清晰；
5. 低饱和、明亮、轻量；
6. 使用已有网球图形语言；
7. 能减少的信息就不要增加；
8. 不为了专业感牺牲轻松感；
9. 不为了设计感牺牲可用性；
10. 与现有成熟页面看起来属于同一个产品。

如果页面看起来像赛事后台、电竞比分系统、企业 SaaS 或模板化 AI App，应重新设计。

**球搭子始终应该像一款真实网球爱好者愿意长期放在手机里使用的赛事与球友工具。**
