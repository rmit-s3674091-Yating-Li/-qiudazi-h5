# V8 Discovery｜Trust without a Social Network

> 日期：2026-10-02
> 阶段：POST-V7 DISCOVERY / NEXT-VERSION PLANNING
> 状态：DECISION_CANDIDATE
> 边界：研究记录，不构成实现任务、产品 canonical 或发布授权。

## 原始产品问题

如果 V8 继续研究“邀请 → 成局 → Play Again”，用户在半熟人、朋友的朋友、临时补位或公开赛事中，究竟需要看到什么信息，才愿意和一个不完全认识的人打球？是否必须先建设好友、关注、私信、公开评分和实名验证，还是已有共同参赛历史本身就能形成足够的情境信任？

## 来源 / 证据

- Airbnb 当前把身份验证放在高风险交易动作附近：预订用户需要验证身份；预订前房东看到的是受限资料，头像在预订确认前隐藏，但可看到名字、身份验证状态和评价。身份验证被明确描述为降低欺诈/提升信心，而非“保证此人一定是谁”。
- Meetup 当前把“是否真的参加过活动”做成可持续的事件关系：组织者可 check-in / no-show / not coming，并在后续 attendee list 中区分首次参加和曾参加过活动的人；同时公开 profile 只承担较轻的个人介绍与共同兴趣。其成员间消息能力还受到订阅和关系条件限制，并非默认开放所有陌生人私聊。
- Strava 把 Profile、Activity、Group Activity、Map 等可见性拆开控制。用户可以让活动仅 Followers 可见，Group Activity 也可单独限制；说明“社交身份可见”与“某次共同活动关系可见”不必绑定成一个总开关。

## Function pattern

1. **Contextual trust before global reputation**：先利用“谁邀请的 / 是否共同参加过 / 最近一起打过几次 / 是否同一小组”等上下文信号，而不是立即建设全站星级评分。
2. **Progressive identity**：低风险浏览或邀请落地只展示最少身份；当用户进入更高风险动作（公开补位、陌生人局、付费或未来需要责任追溯的动作）时，再逐级增加验证要求。
3. **Attendance as evidence**：区分 RSVP 与真实到场。若未来需要可靠性信号，应优先研究“参加过几场 / 最近共同参赛 / no-show 事实”而不是主观五星评价。
4. **Relationship-scoped visibility**：共同赛事、固定小组、Club 成员可看到比陌生人更多的信息；不必默认建立全站公开社交图谱。
5. **Trust signals ≠ contact graph**：建立信任不意味着必须同时拥有好友、关注、Feed、DM。

## UI / UX pattern

- 邀请/补位卡片优先显示情境：`Grace 邀请你`、`你们上次一起打过`、`2 位你打过的球友已参加`，而不是先展示复杂个人主页。
- 陌生参与者可使用轻量 profile sheet：头像/显示名 + 与本场有关的有限信息 + 共同关系信号；更深资料按关系或动作逐步披露。
- “已验证”若未来存在，应作为小型 trust badge，而不是页面主视觉；必须明确验证证明什么、不证明什么。
- 组织者侧可以看到 RSVP / checked-in / no-show 等运营状态，普通参与者不必看到全部管理信息。
- 隐私设置应按信息对象拆分（profile / participation / group relationship / precise location），避免一个“公开/私密”总开关承担所有语义。

## Why it works

球搭子的核心行为是现实见面和共同运动。对这种产品，最有解释力的信任往往来自“我为什么会遇到这个人”以及“这个人是否真的参与过”，而不是脱离场景的粉丝数或五星均分。情境信任还可以直接复用已有赛事历史，从而避免为了陌生人匹配过早建设完整社交基础设施。

## Applicability

- **高**：朋友的朋友、固定小组、Club 内活动、过去共同参赛者、轻量补位。
- **中**：公开赛事大厅中的陌生人报名，需要进一步验证真实风险和组织者筛选需求。
- **低/待验证**：高价值交易、未成年人、涉及支付/场馆责任的场景，可能需要更强身份与安全机制，不能用轻量信任替代。

## Counterexamples / Risks

- Airbnb 的强身份验证服务于住宿/交易和现实安全，直接照搬到普通约球会增加 onboarding 成本和敏感数据处理范围。
- 五星评分会把一次迟到、竞技水平、社交偏好、人格评价混在一起，容易产生报复性评分、歧视和新用户冷启动问题。
- “参加过很多场”不等于“可靠”或“安全”；历史次数只能是上下文，不能包装成安全认证。
- no-show 也可能由组织者临时改时间、天气或系统状态不同步造成；未经事实校验不应直接变成公开声誉惩罚。
- 公开真实姓名、精确地点、历史参赛轨迹会扩大隐私风险；尤其不能因为要做信任而默认公开完整运动轨迹。

## 球搭子可能含义

V8 若验证 R-001 / R-004 的“Play Again + commitment loop”，身份与关系层的最小候选不应是“好友系统”。更小的解可能是：

**邀请来源 + 共同参赛历史 + 本场参与状态 + 可复用小组关系 → 足够的情境信任。**

只有当真实研究证明陌生人补位是高频且用户确实因“不知道对方是谁”而放弃成局，才值得把实名/验证/公开 reputation 提升为 V8 范围候选。

## Smallest validation

不开发。制作同一个“还差 1 人”的三种静态参与者卡：

- A：只有头像 + 昵称；
- B：头像 + 昵称 + `你们共同打过 2 场 / 由 XX 邀请 / 2 位你认识的球友已参加`；
- C：头像 + 昵称 + 实名验证 badge + 评分 + 总参赛次数。

让 5–8 位真实用户回答：哪张卡已经足够让你决定是否参加？缺的究竟是什么信息？然后分别测试“熟人邀请”“朋友的朋友”“完全陌生公开补位”三个场景，避免把不同风险级别混为一个需求。

同时询问组织者：判断一个临时补位者时，最想知道的是水平、共同认识的人、历史到场、身份真实性，还是其他信息。

## 建议优先级

**中高研究优先级；实现优先级未定。**

证据：跨行业模式中强；球搭子自身需求证据弱。它会直接决定未来是否需要好友、公开 profile、实名、评分和陌生人匹配，因此值得在这些高成本能力之前验证。

## 未决问题

- “共同打过”是否比“共同好友/共同小组”更有信任价值？
- 球搭子是否需要区分 `RSVP` 与 `实际到场`，以及谁有权确认到场？
- 双打搭档关系应是长期关系，还是赛事历史推导出的轻量上下文？
- 陌生人补位究竟是否足够高频，值得扩大身份与隐私处理范围？
- 哪些 trust signal 应只给组织者看，哪些可给普通参赛者看？

## 与既有研究的关系

该结论补充 R-001（Play Again）、R-002（固定小组）和 R-004（邀请承诺漏斗）：即使未来需要“补人”，也不应默认通过完整社交网络解决。应先验证能否利用赛事上下文建立最低必要信任。若后续真实用户证据否定陌生人补位需求，本候选应降级，而不是继续扩张身份/社交范围。
