# V8｜多人状态与同步信心研究

- 日期：2026-10-02
- 状态：DECISION_CANDIDATE
- 主题：实时多人状态 / 弱网 / 冲突恢复
- 边界：研究记录，不构成开发任务。

## 原始产品问题

V7 已有多人赛事与记分场景。下一版本若继续强化现场协作，关键问题不是“能否实时刷新”，而是两个人同时操作、网络短暂中断或提交尚未确认时，用户是否知道当前状态是否已保存、谁正在操作、失败后该怎么办。

## Function pattern

成熟协作产品共同体现出一条分层原则：正常状态自动同步；只有状态影响用户决策时才展示 presence；pending、unsent、error 应可区分；失败操作需要明确恢复路径；高冲突、高后果动作才考虑版本校验或窄范围互斥，而不是默认全页面锁定。

## UI/UX pattern

正常成功应安静，不持续弹“同步成功”；短暂 pending 用局部状态表达；持续失败再升级为明确 inline/banner，并说明“未保存/未同步”以及下一动作。多人同时操作时，只在相关对象附近表达“某人正在处理”，不把协作工具式 cursor/presence 全量搬进比赛页。比分等高后果动作若尚未确认，不应通过乐观界面伪装成最终成功。

## 来源 / 参考产品

Notion 支持多人同时编辑、协作者位置、即时更新与历史；其离线说明明确指出，非文本属性在离线冲突时可能只有一个更新最终保存。Linear 的协作编辑显示他人光标并实时保存同步。Trello 移动端提供 sync indicator、Sync Queue 与 unsent changes 警告；Web 断连时直接提示编辑不会同步保存。

## Why it works

它把“系统是否接受了我的动作”与技术层的实时刷新分开。成熟协作产品不会要求用户理解同步机制，但在可能丢失数据时显著提高状态可见性；正常路径保持低噪音，异常路径才提高反馈强度。

## Applicability

高：记分、开赛/结束、搭档或参赛状态等多人可能同时操作且结果改变下一步的场景。
低：只读赛事详情、照片浏览等不存在竞争写入的页面。

## Counterexample / 风险

照搬 Figma/Notion 的全量 presence、锁定和版本历史会明显过重。“实时”也不能等同于频繁轮询加到处显示同步提示，否则会增加移动端噪音。反过来，对比分等关键结构化状态完全采用 last-write-wins 又可能隐藏真实冲突。

## 球搭子含义

若现场操作被验证为高摩擦，V8 应优先研究轻量 Sync Confidence：用户始终能判断“已确认 / 正在提交 / 未同步”，再依据真实冲突频率决定是否需要更重的多人协调。它属于 Event-day Operations 的基础质量能力，而不是新的独立功能中心。

## Smallest validation

不开发。用四个静态/可点击场景测试：正常提交；提交后短暂 pending；断网后未同步；两人几乎同时改同一比分。让用户回答“现在谁的数据算数、是否已经保存、下一步该做什么”。同时复盘真实现场是否发生重复点击、双方同时录分、弱网后不确定是否成功等事件；若频率低，只保留异常反馈原则，不扩大为 V8 主功能。

## Suggested priority

中高。研究价值高；是否进入 V8 取决于 Event-day Operations 的真实用户证据。

## 未决问题

哪些动作允许乐观更新；比分是否需要版本校验或确认者；弱网是否需要本地队列；presence 粒度；普通参赛者与组织者的写入边界。
