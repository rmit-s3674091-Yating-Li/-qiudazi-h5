## R-001｜从“一场赛事”转向“下一场球”

- 日期：2026-10-01
- 状态：DECISION_CANDIDATE
- 研究主题：V7 发布后的留存/复用主轴
- 用户问题：V7 已覆盖创建、报名/参赛、对阵、记分、结果、赛事照片与静态场地等单场赛事链路，但尚无证据证明用户完成一场球后，能低成本形成下一场球。
- 来源/证据：V7 已发布产品基线；公开竞品研究显示多款运动组织产品把 recurring sessions、RSVP、waitlist、固定 group/crew 作为持续复用机制。
- 竞品模式：PickleBuddy 提供 recurring sessions + binary RSVP + auto-fill waitlist；PlayMore 提供 upcoming sessions、RSVP、waitlist 与邀请；Dink On Time 支持 one-time/recurring games、core players/subs 与自动 waitlist；The Crew 将 recurring sessions、RSVP、waitlist、历史记录串成 weekly crew loop。
- 球搭子含义：下一版本不宜默认继续增加赛事管理功能；优先验证“Play Again / Find Next Game”是否比“更多赛事能力”更能提高复用。
- 风险/反例：真实用户可能已经通过微信群稳定约球，补位/复约并非主要痛点；公开竞品模式不能证明中国目标用户同样需要。
- 最小验证：访谈 5–8 位真实组织者/参赛者，复盘最近 3 次打球从上一场结束到下一场成局的过程；用静态概念原型比较“再来一场 / 还差 1 人 / 和这些人再约”三类入口，不开发。
- 建议优先级：高（证据强度：竞品中强；球搭子自身用户证据：弱，必须先验证）
- 未决问题：核心留存摩擦究竟是“找人”“定时间”“定场地”还是“重复创建/通知”。

## R-002｜复约的第一层应先验证“固定小组 + 周期场次”，而不是完整社交网络

- 日期：2026-10-01
- 状态：DECISION_CANDIDATE
- 研究主题：Play Again 的最小产品形态
- 用户问题：如果用户经常与同一批人打球，逐场重新建赛事、重新邀请、重新确认出席会把重复组织成本留给组织者；但直接建设好友、Feed、群聊、陌生人推荐会显著扩大产品与治理范围。
- 来源/证据：公开产品资料显示，PickleBuddy、Dink On Time、Court10、The Crew、CourtValet 都把 recurring game/session 与 group/crew 关系结合；Court10 进一步用 group availability 先找共同空闲时间；The Crew 将每次 session 纳入同一 crew 历史。
- 竞品模式：共同最小闭环是“已有一组人 → 建一次/周期场次 → RSVP → 缺位候补/补位 → 下一周期复用”，而非必须先建设开放社交网络。
- 球搭子含义：若 R-001 被用户验证，建议下一步优先比较两种轻量方案：A. 从已结束赛事复制/复约；B. 建立可复用的小组/常用参赛组合 + 周期场次。完整好友体系、公开 Feed、DM、Rating 暂缓。
- 风险/反例：固定小组需要稳定身份/成员关系；周期场次涉及单次取消、成员变化、系列与单场数据模型边界。若多数赛事是一次性陌生人局，固定小组价值会下降。
- 最小验证：不用代码，给组织者两张低保真流程图——“复制上一场”与“固定小组每周自动生成待确认场次”；观察其真实偏好，并询问愿意维护成员名单还是只想复制赛事。
- 建议优先级：高（前置依赖 R-001 用户验证）
- 未决问题：是否需要真正的 Group 实体，还是“最近参赛者/常用阵容 + 复制赛事”已经足够；周期场次应自动创建还是只生成待确认草稿。

## R-003｜“找共同时间”可能比“找更多陌生球友”更值得先验证

- 日期：2026-10-01
- 状态：HYPOTHESIS
- 研究主题：复约链路中的协调摩擦
- 用户问题：固定球友存在时，组织失败可能不是缺人，而是群聊反复询问“哪天有空”。
- 来源/证据：Court10 公开产品将 weekly group availability 和重叠时间识别作为核心差异；其他多款产品则以 RSVP/提醒处理已确定时间后的出席确认。
- 竞品模式：把“决定什么时候打”与“确定谁参加”拆成 availability → session → RSVP 两步。
- 球搭子含义：在研究“找陌生人补位”之前，应先问用户真正耗时的是人数不足还是时间协调。若时间协调更高频，可考虑轻量 availability poll/时间候选，而不是直接做公开匹配。
- 风险/反例：增加 availability 会引入更多输入成本；微信群投票可能已经足够；持续共享日程/空闲时间会增加隐私负担，不应默认采用。
- 最小验证：访谈中记录最近 3 次约球从提出到定局分别花在“找人 / 定时间 / 定场 / 催确认”的时间；只测试一次性 2–3 个候选时间投票概念，不测试日历读取或持续可用性共享。
- 建议优先级：中（作为 R-001 访谈的诊断问题，不单独开发）
- 未决问题：一次性时间投票是否足够；是否值得与“再来一场”合并成同一入口。

## R-004｜邀请不应只是“分享链接”，而应研究成“低摩擦承诺漏斗”

- 日期：2026-10-01
- 状态：DECISION_CANDIDATE
- 研究主题：邀请传播 → 参赛承诺 → 成局的跨行业模式
- 原始产品问题：球搭子的价值不在链接被发出去，而在被邀请者是否快速理解“这是什么、谁在、何时何地、我现在要做什么”，并完成足够明确的参赛承诺；组织者同时需要知道谁尚未回应、谁可能参加、满员后如何补位，而不是继续在群聊中人工追问。
- 来源/证据：Partiful 当前公开资料显示，活动可用单一链接传播，访客可在浏览器完成 RSVP；主办方实时看到响应，系统支持自动提醒、guest cap、waitlist、guest approval、+1、cohost、活动后共享照片。Partiful 的 Find a Time 又把日期投票与 RSVP 连成同一状态机：Yes/No/Maybe 投票后，主办方选定时间，响应自动转为 RSVP。Luma 将 event page → registration → confirmation/calendar invite → reminders 组织成连续流程，并支持 Public/Private/Member-Only、approved guest 后才显示精确地点，以及注册后提示用户分享带归因的 referral link。Eventbrite 的 waitlist 则把空位释放设计为有响应时限的 offer，而不是无限期占位。
- 参考产品/行业：Partiful（轻活动邀请）、Luma（活动注册/传播）、Eventbrite（容量与候补）；对应球搭子的不是“票务”，而是多人活动中的 commitment management。
- Function pattern：① 一个可传播的活动入口承载核心事实与单一主动作；② 先允许低摩擦回应，再按必要性收集信息；③ Invited / Maybe / Going / Pending / Waitlist 等状态对组织者可操作；④ 未回应、临近活动、状态变化由系统提醒而非组织者逐个催；⑤ 满员后的候补与空位释放有明确规则；⑥ 分享可继续发生在 RSVP 后，把已承诺参与者变成自然传播节点。
- UI/UX pattern：首屏优先呈现活动身份、时间、地点/范围、关键参与信号与一个高显著 CTA；高级设置藏在 host settings，不让普通参与者看到组织复杂度。响应动作尽量一跳完成；管理侧按状态分组而不是一张无差别名单。时间尚未确定时，不强迫先“创建完整赛事”，而可先显示候选时间投票，选定后平滑转成正式 RSVP。敏感地点可渐进披露，而不是发现页直接暴露精确地址。
- Why it works：把“传播”“理解”“回应”“确认”“提醒”“补位”视为一个连续漏斗，减少用户跨微信群/表单/赛事页反复同步状态的成本；同时把复杂度留给系统和组织者侧，参与者只需做当前最小决策。
- 球搭子可能含义：V8 若验证 R-001 的复约方向，邀请能力不应优先扩成更多分享渠道或更花哨分享卡，而应先验证“被邀请者首次打开后的承诺转化”以及“组织者追人/补位成本”。这与 R-003 可形成一条更完整假设：时间未定时先轻量投票；时间确定后进入 RSVP；满员后进入候补；赛后再进入 Play Again。
- Applicability：高适用于熟人/半熟人小局、双打补位、周期场次和组织者反复催确认的场景；对纯公开大型赛事，可能需要更正式的报名审核与资格规则，不能直接套轻聚会模式。
- 风险/反例：状态过多会增加认知负担；中国用户若天然在微信群完成确认，强制站内 RSVP 可能反而增加一步；Partiful 的“无需账户即可 RSVP”原则不能直接照搬到需要身份绑定、战绩归属或权限控制的球搭子流程；公开显示参与者也涉及隐私与社交压力。Luma/Eventbrite 的票务级管理对小规模约球明显过重。
- 最小验证：不开发。做两套手机低保真邀请落地页：A=当前式“赛事详情 + 报名”；B=“谁约你/什么时候/哪里/还差几人 + 参加/不确定/不参加”单一承诺页。让 5–8 位组织者各拿最近一次真实邀请逐步复盘，并让参赛者完成一次任务测试；观察是否能在不解释的情况下完成回应，以及组织者是否更想要“未回应/不确定/候补”视图。另用一个“时间未定”版本测试 2–3 个候选时间 → 选定 → 自动转确认的理解度。
- 建议优先级：高（研究优先级；产品证据强度：跨行业中强，球搭子自身证据仍弱）
- 未决问题：球搭子最小状态集究竟应是 Going/Not going 两态，还是需要 Maybe；未登录访客能否安全做临时回应；何时要求绑定正式身份；参与名单默认可见范围；候补是否只在容量型赛事需要。

## R-005｜留存不等于“做排行榜”：先验证轻量进度与共同承诺，而不是全局竞争

- 日期：2026-10-01
- 状态：DECISION_CANDIDATE
- 研究主题：赛后沉淀 / 排名 / 成就 / 复访机制的跨行业模式
- 原始产品问题：V7 已能产生比赛结果与战绩，但“有数据”不等于“有复访理由”。下一版需要判断：用户回来是为了看自己持续进步、和固定球友维持共同承诺，还是为了全局排名；三者对应完全不同的产品复杂度与社交压力。
- 来源/证据：Strava 当前 Club 将成员活动、事件、周榜与 feed 放在同一组织空间；其周榜按运动类型统计，并每周重置，移动端突出 Top 10，同时让未进 Top 10 的用户看到自己附近名次。Strava Challenges 用 progress bar、完成 badge/Trophy Case 表达个人进度。Duolingo Friend Streak 则把连续行为变成双人共同承诺，并公开称拥有至少一个 shared streak 的学习者完成每日课程的可能性高 22%。Discord Community Onboarding 的反面启示是：成熟社区会主动减少新成员一次看到的频道/角色复杂度，而不是把所有机制暴露出来。
- 参考产品/行业：Strava（运动记录、Club、Challenge）、Duolingo（streak/social commitment）、Discord（社区复杂度渐进披露）。
- Function pattern：① 个人进度优先用连续记录、阶段里程碑、历史趋势表达；② 小群体竞争可采用短周期榜单，周期结束即重置，避免永久头部固化；③ 社交激励不一定需要公开 Feed，可以是两人/小组共同目标、轻提醒或里程碑祝贺；④ 成就应来自用户已经完成的核心行为，而不是额外任务体系。
- UI/UX pattern：进度状态放在已有“我的战绩/赛后结果”附近，而不是新增一个重型 Gamification 首页；用简短 progress、最近趋势、个人 best/里程碑降低解释成本。若测试小组榜，优先展示“我 + 附近名次”而不是只展示头部；周期、统计口径和隐私范围必须在界面上可理解。共同承诺可使用轻量 badge/streak/连续参赛提示和 nudge，但不默认增加聊天或公开动态。
- Why it works：个人进度提供内在反馈，小范围共同承诺提供关系型外在动力；两者都可以建立在已有比赛行为之上，不要求用户额外生产内容。短周期榜比永久总榜更容易让新用户觉得仍有参与空间。
- Applicability：如果 R-001 验证“重复打球/复约”是核心留存问题，则“连续参赛 / 与同一搭档再次成局 / 小组本周参与”可能比全局胜率榜更贴近真实循环；尤其适用于固定双打搭档、小组和未来 Club 候选。
- 风险/反例：全局排行榜会放大水平差异、刷分、规则争议和新用户挫败；streak 会制造压力，且现实运动受天气、伤病、出差和场地影响，不应照搬“每日不断签”；胜率/Rating 在样本少、对手强弱不均时容易被误读。Strava 大型 Club 还存在 feed/leaderboard 能力随规模受限的现实，说明“Club = 无限内容社区”并非天然成立。Discord 的经验也提示，若 V8 同时引入 Club、榜单、Feed、角色、成就，会明显提高首次理解成本。
- 球搭子可能含义：暂不把“排行榜/成就系统”作为 V8 独立主轴。更值得验证的是赛后页面是否需要一个极轻的“继续关系”层：例如最近 N 场、与某搭档连续参赛、个人阶段里程碑、下一场入口；若未来验证 Group/Club，再测试周榜/小组挑战。任何公开全局 Rating、赛季体系、勋章商城暂缓。
- 最小验证：不开发。为同一赛后场景做三张低保真卡片：A=纯战绩（最近结果）；B=个人进度（最近 N 场 + 里程碑/趋势）；C=共同承诺（“你和 X 已连续一起打 3 场 / 再约一场”）。让参赛者选择“哪一张会让你下周愿意再次打开”，并追问其是否愿意让该信息对搭档、小组或公开可见。另对组织者测试“永久总榜”与“每周重置小组榜”，观察哪种更像有用的组织工具而非装饰。
- 建议优先级：中高（研究价值高；进入 V8 实现仍依赖 R-001/R-002 用户验证）
- 未决问题：连续行为应按“场次”还是“周”计算；双打搭档关系是否足够稳定；哪些战绩适合公开；是否存在不竞技但高频参与者需要被正向反馈；未来 Club 的榜单应衡量胜负、参与还是贡献。

## 当前范围建议（研究态，不是开发计划）

### 下一版本优先候选
1. 验证“Play Again / Find Next Game”是否应成为版本主题。
2. 若成立，优先比较“复制上一场”与“固定小组 + 周期场次”两种最小形态。
3. 同时诊断组织摩擦究竟来自找人、定时间、定场还是催确认。
4. 把“邀请/分享”从渠道功能提升为待验证的 commitment funnel：邀请打开 → 最小回应 → 提醒/补位 → 成局；先验证转化摩擦，不先扩分享渠道。
5. 赛后留存优先验证“个人进度 / 共同承诺 / 再约入口”，不默认建设全局排行榜或重型成就系统。

### 暂缓
- 完整好友/关注/Feed/DM 社交网络。
- Rating / 陌生人算法匹配。
- 全局永久排行榜、复杂赛季/勋章体系。
- 附近球场目录/推荐作为版本主轴。
- 会员、收费、支付、抽佣、广告、赞助等商业化实现。
- 票务平台式的重型 registration/CRM；在小规模约球需求被验证前不引入复杂状态与表单。

### 商业假设（仅研究）
若重复组织成本被验证为强痛点，潜在付费方更可能是高频组织者/俱乐部，而不是普通参赛者。公开产品中 DinkPlan 和 The Crew 均采用“玩家免费、组织者高级能力付费”的模式；该模式仅作为后续商业验证参照，不构成球搭子收费决策。
