# 赛事相册动作语义：赛事共享源 / 个人保存 / 设备导出

- 时间：2026-10-02
- 状态：HYPOTHESIS / DECISION_CANDIDATE
- 建议优先级：高

## Original product problem

当前相册同时存在“高清”“分享/保存”“移出我的相册”等动作，但对象语义并不清晰：用户到底是在操作赛事共享照片、自己在 App 内的保存状态，还是手机设备副本？

## Reference products / industries

参考 Apple Photos、Google Photos、共享相册、内容平台收藏/保存、系统 Share Sheet 等成熟模式。

## Function pattern

建议明确拆分三层对象：

1. Event shared photo
   - 赛事共享来源中的照片
   - 是否仍对赛事参与者可见由赛事级权限决定

2. Personal visibility / saved state
   - 当前用户是否把这张照片保留在自己的“个人视图/收藏/归档”中
   - 从个人视图移除不应影响赛事源

3. Device export
   - 保存到手机系统相册
   - 一旦成功导出，后续站内移除不应影响设备副本

如果“我的相册”只是赛事照片引用集合而非真正独立副本，应考虑弱化甚至取消这一概念，避免制造伪文件管理语义。

## UI/UX pattern

- viewer 内不要并排放多个含义接近的“保存”按钮。
- “保存到手机”使用系统 share/save 语义并提供明确成功反馈。
- “保留到我的相册/收藏”若存在，应使用不同图标和文案。
- “从我这里移除”只作用于 personal state，并明确不会删除赛事源。
- 赛事源删除/撤回应进入权限受控的管理动作，不与个人移除混在一起。

## Why it works

成熟产品通常把共享来源、个人收藏和设备副本视为不同生命周期。明确语义能减少用户对“删了别人还能不能看到”“保存到底保存到哪”的误解。

## Applicability to 球搭子

高。当前用户已经明确认为相册 UI 不合理，而动作语义本身会直接决定新 UI 的层级设计。

## Counterexample / Risk

- 如果产品实际上没有独立的 personal save state，就不要为了 UI 好看制造“我的相册”概念。
- 如果赛事源照片与个人副本在数据层完全复制，删除/生命周期规则会更复杂。
- 过多保存入口会造成选择负担。

## Smallest validation

用同一张赛事照片做三种 viewer：
A. 保存到手机 + 分享；
B. 收藏到我的相册 + 保存到手机 + 分享；
C. 仅分享/保存到手机，不存在“我的相册”。

让 5–8 位用户预测每个动作执行后：
- 别人还能否看到；
- 自己在哪里还能找到；
- 手机相册是否存在副本；
- 是否可以恢复。

优先选择用户能准确理解影响范围的模型。

## What not to do yet

暂不做复杂文件夹、相册层级、下载管理器、跨赛事移动照片、AI 分类。
