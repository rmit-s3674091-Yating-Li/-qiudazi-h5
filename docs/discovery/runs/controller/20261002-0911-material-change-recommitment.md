# 赛事关键变更需重新建立承诺

- 时间：2026-10-02
- 状态：HYPOTHESIS / DECISION_CANDIDATE
- 建议优先级：中高

## Product question

赛事已经有人报名后，如果时间、核心地点或赛事状态发生重大变化，产品应把它视为普通编辑，还是一次需要重新建立参与承诺的事件？

## Sources / evidence

跨行业参考 Partiful、Meetup、Eventbrite、Luma 等活动组织产品。成熟活动产品通常会把重要事件变更与普通文案编辑区别处理，通过更新通知、变更提示或再次确认避免参与者继续基于旧事实行动。

## Function pattern

Material change（例如开赛时间明显调整、核心地点更换、赛事取消/恢复）不应等同普通字段修改。

建议验证：
1. 记录变更前后差异；
2. 对已承诺参与者发出明确变更提示；
3. 提供“仍参加 / 更新回应”这一类轻量重新确认；
4. 组织者能看到哪些人已确认新条件、哪些人尚未回应。

普通描述、备注或非关键视觉信息变化不触发重新承诺。

## UI/UX pattern

- 赛事详情顶部使用轻量 change banner，而不是把所有变化塞进通知中心。
- 明确显示“什么变了”，避免只写“赛事已更新”。
- 主操作优先是“仍参加 / 更新回应”，不要让用户重新走完整报名流程。
- 若赛事取消，应有单独的终止状态，不与普通更新混淆。

## Why it works

用户原来的“参加”是基于一组事实作出的承诺。核心事实变化后，原承诺不应被系统静默继承。差异可见 + 一键重新确认能减少组织者在群聊中逐个解释和追问。

## Applicability to 球搭子

对熟人小局和标准赛事都可能适用，尤其是开赛时间、场馆或取消这类会直接改变参与成本的变化。V8 不应把“报名状态”理解为一次确认后永久有效。

## Counterexample / Risk

- 任何字段变化都要求重新确认会制造通知疲劳。
- 变更等级定义过复杂会把轻赛事做成重型票务系统。
- 若只是场地内球场号、备注、联系人文案等轻微变化，不应打断参与者。
- 需要避免形成过重状态机。

## Smallest validation

不开发。用三类真实场景做低保真测试：
A. 开赛推迟 2 小时；
B. 更换场馆；
C. 赛事取消。

每个场景对比：
1. 静默更新；
2. 显示变更差异；
3. 显示差异 + 一键“仍参加/重新回应”。

观察参赛者能否说清发生了什么、是否知道自己还算不算参加，以及组织者是否减少人工追问。
