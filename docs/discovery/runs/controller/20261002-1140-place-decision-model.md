# 地点决策：已知地点复用 / 候选共同决定 / 未知地点发现

- 时间：2026-10-02
- 状态：HYPOTHESIS / DECISION_CANDIDATE
- 建议优先级：中高

## Product question

“选场地”不是单一问题。球搭子应该如何区分用户已经知道去哪、几个人需要一起决定去哪、以及根本不知道去哪三种情况？

## Function pattern

建议把地点任务拆成三类：

1. 已知地点复用
   - 最近场馆
   - 上一场场馆
   - Club / 固定小组常用场馆
   - 一键复用后再确认

2. 候选共同决定
   - 组织者给 2–3 个候选地点
   - 成员轻量表态/投票
   - 决定后写入正式赛事地点

3. 未知地点发现
   - 用户确实不知道去哪时才进入搜索/发现
   - 需要地图、距离、基础信息和可信来源
   - 不默认把复杂场馆目录作为主流程

## UI/UX pattern

- 创建赛事时优先展示“最近使用 / 上次场馆”，而不是每次从空白搜索开始。
- 若尚未决定地点，可允许“待定”并进入候选协商，不强迫创建时一次完成。
- “找附近场馆”是第三层能力，不应压过复用和共同决定。
- 地点已确认后，详情页聚焦清楚展示、地图查看和导航，不继续暴露发现复杂度。

## Why it works

复用、协商和发现是三个不同 JTBD。把它们混成一个搜索框会让最常见的简单任务也承担发现系统的复杂度。

## Applicability to 球搭子

如果 V8 走“下一场球 / 固定小组 / Club”方向，最近场馆和常用场馆会比完整场馆推荐更直接降低重复组织成本。

## Counterexample / Risk

- 过早建立场馆目录会带来数据质量、营业状态、名称多语言和维护成本。
- 候选投票如果真实用户仍在微信群做，会重复流程。
- 自动推荐“最佳场馆”会进入算法和偏好解释问题，当前证据不足。
- 复用旧场馆时必须允许快速更换，不能把历史变成默认锁定。

## Smallest validation

访谈组织者最近 5 次赛事：
- 有几次地点从一开始就知道？
- 有几次需要大家讨论？
- 有几次真正需要“帮我找一个场馆”？

再比较三个静态入口：
A. 最近/常用场馆；
B. 2–3 个候选共同决定；
C. 搜索附近场馆。

观察用户是否能自然选到符合当前场景的路径。

## Open questions

- 是否需要 Club 默认场馆？
- “待定地点”能否在邀请阶段成立？
- 候选地点是否应与候选时间放在同一协调流程？
- 场馆发现的数据源与双语可信度如何治理，应后置到需求被验证后。
