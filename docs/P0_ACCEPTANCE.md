# 球搭子 H5 MVP｜P0 验收基线（Current）

> 本清单是在早期 H5 P0 Checklist 基础上结合当前讨论更新后的验收基线。早期小程序专属微信登录项不作为当前 H5 测试阻塞项；正式身份接入另行验收。

## A. 身份与档案

- [ ] 首次访问可建立测试登录态并完成昵称资料；返回用户可恢复状态。
- [ ] 当前测试期昵称身份方案不展示 public ID，不误称为正式安全登录。
- [ ] 昵称可编辑；头像 optional，有默认头像。
- [ ] 我的打球档案可维护等级、城市、单双打偏好、常打时间。
- [ ] 昵称/头像编辑与打球档案编辑职责清楚，不出现重复同名编辑页。
- [ ] 用户身份/历史 Player 暂时读取失败时不误导用户“重新创建打球档案”。
- [ ] 未来正式身份接入不得破坏既有 Profile / Player / 历史赛事关联。

## B. 导航与页面职责

- [ ] 底部核心入口保持赛事大厅 / 我的赛事 / 球搭子们 / 我的。
- [ ] 赛事大厅负责发现赛事，不提供创建赛事主入口。
- [ ] 大厅无赛事时展示发现型空状态，可去“我的赛事”。
- [ ] 我的赛事分“我创建的 / 我参与的”。
- [ ] 创建赛事只在“我创建的”等组织者语境提供。
- [ ] 我的战绩与我的赛事职责分离。
- [ ] 球搭子邀请记录与赛事邀请职责分离。

## C. 赛事创建与卡片

- [ ] 创建/编辑赛事支持单打/双打、赛制、计分、名额、日期时间、城市、场地、费用等 P0 字段。
- [ ] Event.city 为独立必填字段，不从 venue 猜测。
- [ ] 等级选项与个人档案一致：2.0及以下 / 2.5 / 3.0 / 3.5 / 4.0 / 4.5及以上。
- [ ] 抢七触发等数值字段类型正确，编辑后可保存。
- [ ] 创建赛事明确选择公开 / 私有。
- [ ] 公开赛事在大厅展示完整公开决策信息；私有赛事也可被发现，但大厅只展示赛事名、城市、级别、单/双打、赛制、状态和明确的私有标识。
- [ ] 私有赛事大厅响应不向未获权限用户下发组织者身份、参赛人、具体日期时间、具体场地、报名人数、候补人数和费用。
- [ ] 公开/私有赛事卡整张卡片视觉可一眼区分，不只依赖两个文字；私有卡保持可点击、非错误/禁用态。
- [ ] 未获权限用户点击私有赛事进入受限预览页；大厅可发现不等于获得完整详情或报名资格。
- [ ] 组织者、明确被邀请人和已报名参与者可读取私有赛事完整详情；仅知道完整赛事 URL / ID 不能绕过后端权限。
- [ ] 公开赛事卡显示组织者头像/昵称/“组织者”、城市、赛事级别、日期时间、场地、报名/名额、费用和基本赛制。

## D. 球搭子与临时 Player

- [ ] “我的球搭子”只展示 accepted Connection。
- [ ] “临时球搭子”只展示当前用户管理且未关联真实用户的 Player。
- [ ] 普通邀请球搭子每次生成独立可追踪邀请记录。
- [ ] 对方完成普通邀请后自动建立 Connection，不增加重复确认。
- [ ] 临时球搭子可继续用于报名、组队和比赛。
- [ ] 临时球搭子完整历史在后台持续积累。
- [ ] 创建者前台不展开临时球搭子的完整战绩/胜率/具体历史比赛，只展示基础管理信息、是否已有记录提示和邀请加入入口。
- [ ] `get_managed_player_profile` 等前端可调用接口不向创建者下发临时球搭子的精确战绩明细，只返回必要基础资料和 `has_history` 等最小信息。
- [ ] 临时球搭子加入后可确认关联既有历史，历史不丢失、不重复。
- [ ] 球搭子邀请记录同时展示普通球搭子邀请和临时球搭子加入/历史关联邀请，并区分类型与状态。
- [ ] 不在 UI 使用“正式球搭子”“claim”“merge Player”“数据迁移”等内部/错误术语。

## E. 报名与邀请

- [ ] 单打报名生成一个 Entry + 一个 Player。
- [ ] 双打报名生成一个 Entry + 两个 Player，不拆成两个 Entry。
- [ ] 接受普通赛事邀请后仍需完成报名；未生成有效 Entry 前不出现在“我参与的”。
- [ ] 真实球搭子由本人接受赛事/搭档邀请并参与最终报名流程。
- [ ] 临时球搭子可由组织者在现实同意前提下代报名。
- [ ] 双打搭档接受组队邀请不等于最终报名完成，最终 Entry 由报名流程创建。
- [ ] 公开赛事组织者可邀请球搭子参赛；已经实际报名的普通参与者也可通过“喊球搭子一起来”邀请自己的 Connection，邀请不会授予赛事管理权限。
- [ ] 未完成公开赛事报名的普通浏览者不能发正式参赛邀请，但可以分享公开赛事链接。
- [ ] 私有赛事普通参赛邀请由组织者控制；未获权限用户分享私有赛事只传播脱敏预览，不授予详情/报名资格。
- [ ] 私有双打中已有合法访问/参赛资格的用户可邀请自己的球搭子组队，搭档获得完成组队所需的赛事访问资格，但不获得管理权限。
- [ ] 单打“邀请参赛”只表示一起参加同一赛事，不承诺双方一定对阵；双打“邀请组队”语义独立。
- [ ] 普通赛事邀请和双打组队邀请可在同一赛事/同一用户之间分别存在，不因唯一约束互相覆盖。
- [ ] 赛事邀请卡提供足够决策信息：日期、城市/场地、级别、单/双打或组队类型。
- [ ] 待回应邀请优先展示；接受为主操作、暂不参加为次操作、查看赛事为低强调详情入口。
- [ ] 正式名额、候补最多 2 Entry、退赛和自动递补正确。
- [ ] 名单锁定后遵守不可继续报名/递补等状态规则。

## F. 编排与比赛

- [ ] 单循环 circle method；奇数 Entry 正确轮空。
- [ ] 单淘汰按 2 的幂生成签表，Bye 第一轮自动晋级。
- [ ] 小组 + 淘汰支持蛇形均衡分组、组内循环、每组前 N 晋级和合理淘汰种子。
- [ ] 未生成对阵/排名时展示真实结构框架或空状态，不伪造选手、比分、名次。
- [ ] 未开赛前按规则允许重新生成对阵。
- [ ] 非法比分不能保存。
- [ ] 计分、完赛、排名、晋级正确联动。
- [ ] 已影响下游比赛的上游结果不能无保护直接覆盖。
- [ ] 比赛结果修正遵守级联保护规则。

## G. 分享与赛后

- [ ] HashRouter 下赛事分享 URL 可直接打开正确赛事。
- [ ] 分享进入后保留赛事/邀请上下文。
- [ ] 赛事邀请、球搭子邀请、历史关联邀请 token 作用域正确，不能互相误判。
- [ ] 私有赛事受限预览分享 URL 不泄露完整详情，也不提升接收者权限。
- [ ] 赛后合影可真实上传/查看并遵守权限。
- [ ] H5 合影以系统照片选择/上传为 P0 主路径，不因进入页面主动申请摄像头权限。

## H. 性能、缓存与反馈

- [ ] Profile 可在安全匹配当前 session 的前提下使用本地缓存加快恢复。
- [ ] 身份/权限敏感页面不能仅依据可能过期的本地 Profile 缓存决定组织者权限。
- [ ] 同一业务数据在多个页面/摘要中使用统一 cache key，不重复请求同一 RPC。
- [ ] 已有缓存时页面不因后台刷新重新变成空白全屏 Loading。
- [ ] 稳定页面不做 10/15 秒固定轮询。
- [ ] 进行中赛事详情/实时记分等确有多人变化的场景可保留较短刷新。
- [ ] mutation 后精准 invalidate 相关缓存，返回列表不会长时间显示旧状态。
- [ ] 用户可见错误不暴露 Supabase/JWT/SQL/RPC 原始技术文本。

## I. 数据与权限

- [ ] 多用户访问共享同一 Supabase 数据，刷新/换设备后数据持久化。
- [ ] RLS/RPC/服务端状态检查保证关键权限，不能只依赖前端按钮隐藏。
- [ ] 临时球搭子详情仅其管理者可访问；其他 authenticated 用户不可读取受限详情。
- [ ] Connection 详情只对已建立关系的用户开放。
- [ ] migration 文件版本唯一、顺序清晰，可用于新环境重放。
- [ ] 新增字段完成 DB → RPC/repository → type → form → UI → filter/cache 的全链路。

## J. 部署前

- [ ] 删除已被新页面替代的死代码和旧术语，避免后续误改。
- [ ] 对照 `PRODUCT_BASELINE.md`、`INTERACTION_BASELINE.md`、`VISUAL_DESIGN_BASELINE.md` 检查设计原则是否偏移。
- [ ] 所有多动作卡片至少在 390px 及更窄视口检查：按钮/热区不碰撞、不重叠，文字不挤压，Primary / Secondary / 详情入口层级清楚。
- [ ] 完成一次针对当前新 head 的部署前综合审计；若同一 head 已审计，不因每小时 routine 重复审计。
- [ ] 区分代码构建失败与 Vercel 平台 build-rate-limit 等外部限制。
- [ ] 中国区 CloudBase 手动部署后进行真机核心 E2E。
- [ ] 未经测试确认不自动 merge `main`。
