# 球搭子 H5 MVP｜P0 验收基线（Current）

> 本清单是在早期 H5 P0 Checklist 基础上结合当前 V6 产品规则更新后的长期验收基线。早期小程序专属微信登录项不作为当前 H5 测试阻塞项；正式身份接入另行验收。

## A. 身份与档案
- [ ] 首次访问可建立测试登录态并完成昵称资料；返回用户可恢复状态。
- [ ] 当前测试期昵称身份方案不展示 public ID，不误称为正式安全登录。
- [ ] 昵称可编辑；头像 optional，有默认头像；打球档案可维护参赛级别、城市、单双打偏好、常打时间。
- [ ] 用户身份/历史 Player 暂时读取失败时不误导用户重新创建档案。
- [ ] 未来正式身份接入不得破坏既有 Profile / Player / 历史赛事关联。
- [ ] 旧 auth session → canonical Profile alias 恢复场景下，服务端仍正确识别赛事角色。

## B. 导航与页面职责
- [ ] 底部核心入口保持赛事大厅 / 我的赛事 / 球搭子们 / 我的。
- [ ] 大厅负责发现，不提供创建赛事主入口；创建赛事只在组织者语境提供。
- [ ] 我的赛事分“我创建的 / 我参与的”，我的战绩、球搭子邀请记录职责独立。
- [ ] “我参与的”按实际有效 Entry/Player 参与事实判断；双打 Entry 中两名已关联真实用户的搭档都能看到赛事。
- [ ] 仅接受赛事邀请或双打组队邀请、尚未形成有效 Entry 时不得提前进入“我参与的”。

## C. 赛事创建、参赛建议级别与卡片
- [ ] 创建/编辑支持单打/双打、赛制、计分、名额、比赛日期、开赛时间、城市、场地、费用等 P0 字段。
- [ ] Event.city 独立必填，不从 venue 猜测。
- [ ] 用户侧只使用“参赛建议级别”区间：2.0及以下 / 2.5 / 3.0 / 3.5 / 4.0 / 4.5及以上；支持不限、单边、同档、区间，最低不得高于最高。
- [ ] 参赛建议级别仅用于发现/匹配，不作为硬报名资格；旧单值 level 仅兼容，不重新成为用户筛选概念。
- [ ] 创建赛事明确选择公开 / 私有。
- [ ] 公开赛事展示完整决策信息；私有赛事大厅仅展示赛事名、城市、参赛建议级别、单/双打、赛制、状态和私有标识。
- [ ] 私有大厅响应不向未授权用户下发组织者、参赛人、具体日期时间、场地、报名/候补人数、费用、registration deadline。
- [ ] 私有赛事可点击进入受限预览；大厅可发现不等于详情权限或报名资格。
- [ ] 组织者、明确被邀请人和已报名参与者可读取私有赛事完整详情；仅知道 URL/ID 不能绕过后端权限。

## D. 报名截止与生命周期
- [ ] 最晚报名时间默认开赛前2小时；组织者只能设置得更早，不能晚于该边界。
- [ ] 创建/编辑表单按比赛日期 → 开赛时间 → 最晚报名时间表达。
- [ ] 修改日期/开赛时间导致截止不合法时自动收紧并明确提示“已自动调整”。
- [ ] 截止前1秒普通报名可成功；到截止瞬间及之后普通名单变更失败，以服务器时间为准。
- [ ] 截止后单打/双打报名、组织者代临时 Player 报名、双打最终 Entry、普通/双打邀请接受、普通退赛均不能绕过。
- [ ] 提前打开旧页面、旧分享深链和直接 RPC 调用在截止后同样失败。
- [ ] 截止后即使 pg_cron 尚未物理更新状态，列表和服务端权限立即按 locked 语义处理。
- [ ] 报名截止但人数不足时使用明确状态/文案“报名已截止，但当前人数不足以编排”。
- [ ] 公开/完整卡截止提示不做秒级轮询：>24h 具体时间；1–24h 约 N 小时；<1h 即将截止；过期已截止/已结束。
- [ ] 私有脱敏卡不显示截止、比赛时间或可反推活动时间的信息。

## E. 球搭子、临时 Player、报名与邀请
- [ ] “我的球搭子”只展示 accepted Connection；“临时球搭子”只展示当前用户管理且未关联真实用户的 Player。
- [ ] 临时球搭子完整历史后台持续积累，但创建者前台/RPC只获得必要基础资料 + has_history，不下发精确战绩。
- [ ] 单打报名生成一个 Entry + 一个 Player；双打生成一个 Entry + 两个 Player，不拆成两个 Entry。
- [ ] 报名开放期间，双打 Entry 中任一已关联当前真实用户的 Player 都能从正常赛事 UI 退出整个 Entry，包括不是 `signup_user_id` 的第二位真实搭档；报名截止或名单锁定后双方均不得退出，页面也不得继续使用“查看/退出”等暗示可退赛的文案。
- [ ] 接受普通赛事邀请后仍需完成报名；双打搭档接受组队邀请不等于最终 Entry 已完成。
- [ ] 临时球搭子可由组织者在现实同意前提下代报名。
- [ ] 公开赛事组织者和已实际报名参与者可邀请自己的 Connection；未报名浏览者只能分享公开链接。
- [ ] 私有赛事普通参赛邀请由组织者控制；私有双打中已有合法访问/参赛资格的用户可邀请自己的球搭子组队，搭档只获得完成组队所需权限。
- [ ] 普通赛事邀请和双打组队邀请记录语义/唯一性独立。
- [ ] 正式名额、候补最多2 Entry、退赛和自动递补正确；名单锁定后遵守不可继续报名/递补规则。

## F. 权威赛事身份与管理入口
- [ ] `get_event_snapshot` 等服务端快照返回的 `viewer_role` 是赛事详情角色判断权威依据。
- [ ] EventPage 不得仅通过本地 `auth.profile.id === event.owner_user_id` 判断组织者。
- [ ] MatchPage 的比赛详情、实时记分、直接录入比分与比分更正同样以 `viewer_role === 'owner'` 判断组织者记分能力；不得仅依赖本地 Profile ID。
- [ ] MatchPage 本地比分级联预演需要 actor ID 时使用快照中的 canonical `event.owner_user_id`，不使用可能过期的本地 `auth.profile.id`。
- [ ] owner / invited / participant / viewer 的前端入口与服务端权限一致；前端隐藏按钮不能替代后端授权。
- [ ] 实际有效 Entry 中的 Player membership 优先识别为 participant；双打两名已关联真实用户的搭档在 snapshot/preview 中均按实际参与事实获得正确角色/访问，不因 signup_user_id 或历史 accepted invite 被误判。
- [ ] canonical Profile alias/旧 session 场景中合法组织者仍能看到并使用管理、编辑、编排、开赛、实时记分、直接录分和比分更正等应有入口。

## G. 设置、隐私与语言
- [ ] “我的 → 设置与隐私”可真实保存设置。
- [ ] 头像、水平级别、常打城市、约球时间、单双打偏好按字段控制球搭子浏览可见性；昵称和赛事共同事实不受影响。
- [ ] 隐私设置不隐藏合法赛事参与者应共享的名单、比分、赛果。
- [ ] “允许赛事邀请”“允许双打组队邀请”为独立开关且默认开启，后端 RPC 实际执行。
- [ ] 设置与隐私提供“我的上传内容/赛事照片”管理；有删除权的用户可看到自己管理的赛事照片并发起一键删除。
- [ ] 删除赛事照片必须二次确认并明确不可恢复；服务端校验删除权并一致性清理 photo metadata、高清原图、水印预览，不允许客户端通过任意 Storage path 删除他人对象。
- [ ] 删除成功后隐私页记录消失，赛事照片 Tab 恢复为空态；失败不得误报成功且可安全重试。
- [ ] 简体中文 / English 可切换且本地持久化。
- [ ] 英文模式核心流程完整覆盖：大厅、我的赛事、详情、创建/编辑、报名/邀请、球搭子、我的、设置，以及核心状态/错误/空状态；不存在影响任务理解的半翻译。
- [ ] 新增核心用户文案进入统一 i18n；业务逻辑不得通过比较中文/英文展示字符串判断报名状态、权限或赛事状态。
- [ ] 375/390/430px 或最接近移动端宽度下检查 English 长文本、Header、Tab/Chip、赛事卡、动作区、Sheet/Modal、照片管理与删除确认，不因英文字符长度出现溢出、遮挡或不可点击。

## H. 编排与比赛
- [ ] 单循环 circle method；奇数 Entry 正确轮空。
- [ ] 单淘汰按2的幂生成签表，Bye 第一轮自动晋级。
- [ ] 小组+淘汰支持蛇形均衡分组、组内循环、每组前N晋级和合理淘汰种子。
- [ ] 未生成对阵/排名时展示真实结构框架或空状态，不伪造选手、比分、名次。
- [ ] 未开赛前按规则允许重新生成对阵；非法比分不能保存。
- [ ] 计分、完赛、排名、晋级正确联动；结果修正遵守下游级联保护。

## I. 分享、赛后、性能与反馈
- [ ] HashRouter 赛事分享 URL 可直接打开正确赛事并保留赛事/邀请上下文。
- [ ] 私有受限预览分享不泄露完整详情，也不提升接收者权限。
- [ ] 赛后合影只允许赛事组织者与有效 Entry 中已关联真实用户的实际参赛者读取；赛事公开不等于照片公开，普通 viewer / 仅 invited 未报名用户无权查看。
- [ ] `event-photos` 使用 private Storage 读取边界；匿名用户和无权 authenticated 用户即使知道对象 path/旧 URL 也不能读取照片。
- [ ] 有权用户默认只加载受保护水印预览，不自动加载高清原图；点击“小眼睛/查看高清”后服务端重新校验 owner/participant 权限并只提供短时高清访问。
- [ ] 水印预览是真实派生资源，不用 CSS blur 高清原图冒充安全预览；高清 URL 不作为长期公开 URL 缓存/展示。
- [ ] 赛事未结束不可上传；赛事结束后只有有权组织者可选择 JPEG/PNG/WebP 上传，H5 不主动申请摄像头。
- [ ] 上传原图与水印预览均成功后才形成有效 photo 记录；失败清理本次孤儿对象；替换成功后旧原图和旧预览被清理。
- [ ] Profile 可在安全匹配 session 前提下缓存，但身份/权限敏感页面不能仅依据可能过期缓存。
- [ ] 同一业务数据统一 cache key；有缓存时后台刷新不清空页面；稳定页面不做固定10/15秒轮询。
- [ ] mutation 后精准 invalidate；用户可见错误不暴露 Supabase/JWT/SQL/RPC 原始技术文本。

## J. 数据、权限与部署前
- [ ] 多用户共享同一 Supabase 数据，刷新/换设备后持久化。
- [ ] RLS/RPC/服务端状态检查保证关键权限；临时球搭子/Connection/私有赛事遵守最小授权。
- [ ] Storage bucket 的 public/private 配置、objects policy、SECURITY DEFINER/RPC execute ACL 与产品隐私规则一致；公开赛事不得成为照片公开读取的旁路。
- [ ] migration 版本唯一、顺序清晰，并通过 clean replay 验证；repository 定义与 live schema/function/Storage 配置一致。
- [ ] 新字段完成 DB → migration → RPC/repository → type → form → list/detail → UI → filter/cache → 验收全链路。
- [ ] 删除已被替代的死代码和旧术语。
- [ ] 对照最新版 PRD、PRODUCT/INTERACTION/VISUAL baseline、P0 与 CHANGELOG；功能行为变化未同步文档时禁止发布。
- [ ] 所有多动作卡片至少在390px及更窄视口检查动作/热区不碰撞、文字不挤压、层级清楚。
- [ ] 完成当前候选 head 的独立代码巡检、全功能测试和 Release Gate；发布相关 P0/P1 必须 VERIFIED。
- [ ] 区分真实代码 build failure 与 Vercel build-rate-limit 等平台限制。
- [ ] 中国区 CloudBase 手动部署后进行真机核心 E2E；未经测试确认不自动 merge `main`。
