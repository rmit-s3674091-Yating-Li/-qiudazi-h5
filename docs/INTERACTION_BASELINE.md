# 球搭子｜页面与交互一致性基线

> 状态：当前 H5 MVP 的 IA / UX 约束。目的不是重新设计视觉，而是把迭代中已经反复遇到的问题固化为规则，避免后续页面再次出现职责重叠、重复入口、状态误导和重复请求。

## 1. 页面职责先于功能堆叠

每个页面先回答“用户来这里主要做什么”，再决定入口。

- 赛事大厅：发现赛事。
- 我的赛事：组织和跟踪与我有关的赛事。
- 球搭子们：管理真实球友关系和临时球搭子。
- 我的：个人资产与设置入口。
- 我的战绩：看比赛结果，不承担赛事管理。
- 球搭子邀请记录：看球搭子关系邀请历史，不承担赛事邀请。

同一个主任务不要因为空状态、快捷方式或“方便”而在多个一级页面重复成为 Primary Action。

## 2. 卡片代表实体，动作代表行为

统一规则：

- 赛事卡片 → 赛事详情。
- 真实球搭子卡片 → TA 的档案。
- 临时球搭子卡片 → 临时球搭子管理/受限档案详情。
- 战绩记录 → 对应比赛/赛事上下文。

“编辑 / 邀请 / 删除 / 报名 / 管理 / 代报名”等必须作为明确动作，不把点击整张实体卡片偷偷解释为“编辑”。

## 3. 展示优先，编辑按需

详情页默认用于阅读。编辑通过铅笔、文字按钮或明确入口进入。

不要因为某对象“可编辑”就让其卡片直接打开表单；也不要让两个页面都叫“编辑档案”却编辑不同字段。昵称头像与打球档案字段应在标题和入口上区分。

## 4. 空状态不能改变页面职责

空状态包含：人话标题 + 一句解释 + 合理下一步。

下一步必须属于该页面职责。例如赛事大厅无赛事时可“去我的赛事”，但不因此把“创建赛事”重新塞回大厅成为主按钮。

空状态文案必须符合真实状态机：

- “我参与的”只在完成报名后出现赛事；不能写“接受邀请后会出现”。
- 无战绩意味着没有已完成比赛，不等于没有参加赛事。
- 无球搭子与无临时 Player 是不同状态。

## 5. 邀请必须区分“关系”和“赛事”

### 球搭子关系邀请

入口在“球搭子们”，历史在“我的 → 球搭子邀请记录”。普通邀请与临时球搭子加入邀请都可记录，但应有清楚的类型标签和状态。

### 赛事邀请

入口和待处理状态归“我的赛事”。接受普通赛事邀请只表示接受邀请意向，不自动生成 Entry；界面必须继续引导完成报名。

### 双打搭档邀请

接受表示同意组队，不等于整个双打 Entry 已完成报名。最终报名动作必须有清晰归属。

## 6. 真实球搭子与临时球搭子

“我的球搭子”与“临时球搭子”必须分 Tab/分组，不混为一个列表。

真实球搭子可查看对方允许展示的长期打球档案和历史战绩。

临时球搭子由创建者管理。后台可以持续积累完整历史，但创建者前台只看到基础管理信息、是否已有历史的提示，以及“邀请 TA 加入球搭子”转化入口；不要展开对方完整战绩价值。

临时球搭子成为用户并关联历史后，才把完整长期档案作为本人可使用的产品资产。

## 7. 赛事卡片信息优先级

移动端卡片不能无限堆字段，但必须支持快速决策。推荐顺序：

1. 状态 + 类型/级别；
2. 赛事名称；
3. 组织者身份；
4. 赛制/计分概要；
5. 日期时间；
6. 城市 + 场地；
7. 报名人数/名额 + 费用。

组织者使用头像 + 昵称 + “组织者”表达，不只放一个没有身份信息的“创建者”标签。

城市和级别属于关键筛选信息，不能因为视觉简化被删掉；没有城市数据时不从场地猜测。

## 8. Primary Action 与移动端动作区规则

一页原则上一个最明显主操作。

当出现两个看似同等重要的动作时，先检查是否其实属于不同页面职责，或者其中一个应放进详情页 / Bottom Sheet / 次级文字按钮。

不要为了“入口多一点方便”让相同动作在多个一级页面重复出现。

移动端动作区必须额外遵守：

- 任何两个相邻按钮之间必须有明确间距，不允许边框、圆角、点击热区视觉上贴合或重叠；不能依赖浏览器对 flex shrink 的偶然结果。
- 两个并列按钮只有在窄屏下仍能保证各自可读、可点且保留间距时才允许横排；否则必须自动改为纵向堆叠。
- 三个及以上动作禁止做成连续的大按钮矩阵。只保留一个 Primary Action；拒绝/取消等为 Secondary Action；“查看详情/查看赛事”这类导航优先使用独立文字链接或低强调入口。
- 同一卡片内的 Primary、Secondary、详情入口必须有视觉层级，不能三个动作看起来同等重要。
- 所有动作布局必须至少检查 390px 及更窄移动端；不得出现按钮文字挤压、图标压文字、按钮互相覆盖、圆角相交或触控区重叠。
- 新增或重构含多个动作的卡片时，部署前必须把“窄屏按钮碰撞/重叠”作为回归检查项，而不是只检查桌面或宽屏截图。

## 9. Loading / Cache / Refresh 体验

已有缓存时不应把页面重新清空成全屏 Loading。页面切换应尽可能保留已知内容并后台刷新。

同一 RPC/同一业务数据在摘要和详情中优先共用 cache key，避免因为组件不同而重复请求。

稳定页面不固定 10/15 秒轮询。只有实时赛事/比分等场景可高频更新。

用户主动刷新必须可强制请求最新数据；mutation 成功后精准 invalidate 对应列表/详情。

## 10. 错误文案

用户错误提示结构：发生了什么 + 用户下一步能做什么。

不要直接展示：

- Failed to fetch；
- JWT / auth session 内部错误；
- SQL/RPC function 名；
- Postgres constraint；
- RLS；
- raw stack trace。

技术错误可留日志，但 UI 应翻译成产品状态。

## 11. 重构与死代码

页面迁移到新实现后，旧整页实现应删除，不能长期保留一套“看起来还能用”的旧 Profile/Player/Event 页面。

原因：后续搜索和 AI 修改极易改错文件，造成“代码改了但页面没变化”或旧术语复活。

允许保留的兼容代码必须明确标注兼容目的和退出条件。

## 12. 数据字段全链路

新增业务字段（例如 Event.city）必须同时检查：

DB schema → migration → RPC / repository → TypeScript type → create/edit form → list/detail response → UI display → filter → cache invalidation → 验收场景。

禁止只在前端新增一个输入框或从其他字符串猜字段。

## 13. 设计一致性检查

新增页面前至少检查一个最相近的现有页面；同一语义操作复用同一组件/class。

不要在一次局部需求中顺便重新定义全局按钮、卡片、颜色、导航或页面职责。若确需改变全局原则，应先明确提出并更新基线文档。

## 14. 部署前审计

较大部署前必须做综合审计，但每小时自动检查只负责判断“是否出现新的、未审计的大改”，不能对同一 head 重复执行完整审计。

完整审计至少覆盖：

- 与 `PRODUCT_BASELINE.md` / 本文件 / `VISUAL_DESIGN_BASELINE.md` 的一致性；
- 核心 E2E 流程和状态机；
- migration 顺序和唯一性；
- RPC/RLS/权限；
- cache key、轮询、写后失效；
- 错误/空状态文案；
- 死代码/旧术语；
- HashRouter 分享深链；
- 前后端字段一致性；
- 所有多动作卡片在 390px 及更窄视口下不存在按钮/热区碰撞、文字挤压或层级混乱；
- 构建/部署状态及平台限额与代码错误的区分。

审计结果必须说明：新增检查范围、阻塞项、已修复项、是否发生设计原则偏移、是否可以进入中国区手动部署测试。
