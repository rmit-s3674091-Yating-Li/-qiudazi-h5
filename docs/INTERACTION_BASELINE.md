# 球搭子｜页面与交互一致性基线

> 状态：当前 H5 MVP 的 IA / UX 约束。照片专项以 `docs/PHOTO_ALBUM_BASELINE.md` 为最终真源；Quick Start 专项以 `docs/QUICK_START_BASELINE.md` 为最终真源。

## 1. 页面职责
- 赛事大厅：发现赛事。
- 我的赛事：组织和跟踪与我有关的赛事。
- 球搭子们：管理真实球友关系和临时球搭子。
- 我的：个人资产与设置入口。
- 我的战绩：已完成比赛结果。
- 参与赛事相册：本人主动保存的比赛照片资产。
- 设置与隐私：个人设置，不承担赛事源照片管理。

同一个主任务不要因为快捷入口在多个一级页面重复成为 Primary Action。

### 1.1 快速开赛主动作
现有四个底部主导航的页面归属与信息架构保持不变。在底部导航正中央增加一个向上凸起的圆形“快速开赛”动作按钮：
- 它是 action，不是第五个长期 Tab；
- 不占用或替换现有四个导航项；
- 不得把“我的战绩”等能力从“我的”中拆出；
- 在四个主导航页均保持同一位置、尺寸和语义；
- 点击后进入独立短流程，成功后直接进入新建赛事管理/对阵上下文。

快速开赛当前交互：
1. 选择单打 / 双打；
2. 选择参赛 Player：本人、accepted Connection 的真实球搭子、本人未认领临时 Player，也可现场新增临时 Player；
3. 若为双打，进入明确“确认双打队友”步骤，逐队显示两名成员并允许调整；不得仅按勾选顺序静默决定最终队友；
4. 设置城市、可选场地、赛制和计分；
5. 点击“一键开赛”。

“一键开赛”成功路径中，系统创建赛事、锁定名单并自动生成首次对阵，然后直接进入赛事管理。正常路径不再把“生成对阵”作为第二个人工任务暴露给用户。

若 Event/Entry 已创建而首次 draw 因网络、Edge 或事务临时失败，页面切换为“开赛未完成 / 恢复开赛”状态；恢复按钮只能对已创建 event 重试 draw，不能再次创建赛事。刷新当前快速开赛页后仍应恢复 pending event。正式开赛前如果人员临时变化，走赛事管理调整/解锁 → 修改名单 → 重新生成；开赛后不允许普通替换 Player。

## 2. 卡片与动作
卡片代表实体，按钮代表行为。赛事卡进入赛事详情；球搭子卡进入 TA 档案；临时 Player 卡进入管理/受限档案；战绩进入比赛/赛事上下文。编辑、删除、报名、邀请、加入相册、移出相册都必须是明确动作。

## 3. “我参与的”与权限
“我参与的”按有效 Entry → active EntryPlayer → Player.linked_user_id 判断；双打两名真实搭档都属于参与者。仅接受邀请但未形成 Entry 不算参与。

赛事详情、编排、记分、比分更正等身份敏感入口必须依赖服务端 `viewer_role` 等权威事实，前端隐藏按钮不能替代后端授权。

## 4. 赛事卡、发现与报名截止
公开/完整标准赛事卡优先展示状态、类型/建议级别、赛事名、组织者、赛制/计分、日期时间、城市+场地、报名/名额+费用。私有标准赛事大厅脱敏卡不得展示精确时间、场地、费用、组织者、参赛人、报名人数或截止时间。

正常 `event_mode='quick'` 赛事进入普通赛事大厅卡片流，默认 public。Quick Event 卡可以展示“快速赛事 / 已锁定”等状态，但不得提供报名/候补 CTA；用户点击后进入赛事详情，权限继续服从服务端。

自动化 QA 组织者（当前 `QA-*` / `QA15-*`）创建的赛事不得出现在公共大厅，无论赛事名称是否带 QA、event_mode 是 standard 还是 quick。QA 数据仍应在测试账号自己的“我的赛事”/直接 URL 中可达。

大厅级别筛选使用单项级别选择；赛事建议范围包含所选级别即可命中，不把筛选变成报名资格。

截止提示只使用已加载 deadline + 本地时钟，不增加轮询；真正可报名性始终由服务端决定。Quick Event 不展示报名截止/候补语义；它从创建成功起即是已确定名单的 locked 赛事。

## 5. 报名与邀请
接受普通赛事邀请后仍需完成报名；接受双打组队邀请也不等于最终 Entry 已建立。截止后所有改变名单的入口和服务端写入都必须同步关闭。

临时 Player “邀请 TA 加入球搭子”属于 Player claim invite，与 Connection / Event / doubles invite 独立。create/get/accept claim invite 在测试 alias 身份下也必须识别同一 canonical profile。

### 5.1 标准赛事锁定与首次编排
标准赛事组织者的正常操作固定为：**锁定名单 → 系统自动生成首次对阵 → 查看/复核对阵 → 开始赛事**。锁定确认文案必须明确“确认后自动生成首次对阵”，不得再告诉用户“锁定不会生成对阵”。正常成功路径不出现额外的首次“生成对阵”人工步骤。

锁定 RPC 成功后立即调用权威 draw engine；若首次 draw 临时失败，UI 必须刷新为真实 locked 状态并提供明确的“继续生成对阵 / Retry draw”恢复动作。该恢复动作只生成当前 locked event 的 draw，不重复锁定、不重新创建赛事、不改变名单。首次 draw 已存在时，主要动作是“查看对阵 / 开始赛事”；“重新生成对阵”和“解锁名单”均为次级、需确认动作。

开赛前 no-show 或人员变化：解锁名单 → 清空现有对阵 → 调整 roster / waitlist → 重新锁定 → 自动重新生成首次对阵。已经有真实比赛开始或结束时禁止解锁或无保护重建签表。

## 6. 移动端动作区
一页原则上只有一个最明显 Primary Action。两个按钮只有在窄屏仍清晰时才横排；三个及以上动作不得连续大按钮矩阵。至少检查 375 / 390 / 430px，尤其是英文长文案、Tab、Sheet、确认框、照片按钮。

赛事详情底部 CTA 在移动端必须保持可读的横向/合理比例布局，按钮文字不得因 flex 挤压变成竖排。

快速开赛中央圆按钮应突出但不遮挡左右导航文字/图标；需在 375 / 390 / 430px 及 iPhone safe-area 下检查。Quick player row 的真实头像与 fallback avatar 都必须保持圆形固定尺寸，不能被文本 flex selector 拉伸。

## 7. Loading / Cache / Refresh
有缓存时不要清空成全屏 Loading。稳定页面不固定 10/15 秒轮询；mutation 成功后精准 invalidate；实时比分才允许高频更新。

## 8. 设置与隐私
设置页承载档案字段可见性、赛事邀请开关、双打邀请开关、参与赛事相册整体可见范围和语言。

**设置与隐私不显示“组织者照片管理”“删除赛事照片”“从赛事相册移除”等入口。** 赛事源相册管理只在对应赛事页面。

参与赛事相册可见范围：
- 仅自己可见（默认）
- 搭子可见

MVP 为整本个人相册级设置，不要求逐张设置。

## 9. 赛事相册交互
赛事照片是受限内容，公开赛事也不等于照片公开。只有 organizer 和 actual participant 可以进入赛事相册内容。

### organizer
赛事结束后在赛事页面：
- 可一次选择一张或多张图片上传；
- 每张源照片有“删除照片”；
- 删除必须二次确认。

确认文案必须明确：删除后照片从赛事相册永久删除，之后不能再被其他参赛者新加入个人相册；**已经被参赛者成功加入自己“参与赛事相册”的个人副本不受影响。**

不要同时设计“从赛事相册移除”和“永久删除”两个近义动作。

### actual participant
赛事页每张当前源照片可以：
- 看受保护水印预览；
- 显式查看短时高清；
- 点击“加入我的参与赛事相册”；
- 加入成功后显示“已加入”。

participant 不能上传、替换、删除赛事源照片。系统不得自动帮用户把所有赛事照片加入个人相册。

### 普通 viewer / invited
无赛事照片内容读取权，也没有“加入我的参与赛事相册”入口。

## 10. 我的 → 参与赛事相册
这里只展示本人主动导入成功的个人副本，按赛事分组。空状态引导用户去自己实际参加过的赛事相册选择照片。

个人副本生命周期与赛事源独立：赛事创建人后续删除源照片，已经导入的个人副本仍正常显示。

本人可以查看受保护水印预览和“移出我的相册”。当前 P0 不要求本人在个人相册中查看高清原图；若后续增加该能力，必须服务端重校验并签发短时 URL。

## 11. 搭子相册查看
若目标用户把参与赛事相册设为“搭子可见”，accepted Connection 可从 TA 档案进入相册。搭子只能看到水印预览；不得提供高清按钮，不下发 Storage path，不提供下载/修改/删除能力。

## 12. 图片安全体验
赛事源和个人副本均放在 private Storage。默认展示真实派生水印预览，不用 CSS blur 高清原图冒充安全预览。赛事上下文高清必须显式触发并使用短时 URL。

## 13. 个人资料编辑导航
“我的打球档案 → 编辑头像与昵称”保存成功后应回到明确来源页并替换当前 history entry；不得再 push 一个新的“我的打球档案”导致左上返回重新进入编辑页。直接 URL 进入编辑页时保留安全 fallback。

## 14. 错误文案
用户错误提示结构：发生了什么 + 下一步。不要展示 Failed to fetch、JWT、SQL/RPC、RLS、Postgres constraint 或 raw stack。

## 15. 数据字段全链路
新增业务字段必须检查 DB schema → migration → RPC/Edge → TypeScript → 页面 → cache invalidation → P0 验收。页面迁移到新实现后，旧自动归档、旧单图、旧隐私页删照片逻辑不得继续成为可达路径。

`event_mode` 是明确业务字段，当前取值为 `standard | quick`，不得靠 deadline 是否为空、status 或名称反推模式。`list_events`、`get_event_snapshot` 与 TypeScript `Event` 必须显式保留该字段。

## 16. 部署前审计
发布前必须检查 PRD / PRODUCT / INTERACTION / QUICK_START / PHOTO_ALBUM / P0 / CHANGELOG 一致性、核心 E2E、migration clean replay、repo/live migration exact version、RLS/RPC/Edge ACL、Storage private 边界、缓存、错误/空状态、英文和 375/390/430px。文档与代码不一致即阻塞发布。
