# 球搭子｜页面与交互一致性基线

> 状态：当前 H5 MVP 的 IA / UX 约束。目的不是重新设计视觉，而是把迭代中已经反复遇到的问题固化为规则，避免后续页面再次出现职责重叠、重复入口、状态误导和重复请求。

## 1. 页面职责先于功能堆叠

每个页面先回答“用户来这里主要做什么”，再决定入口。

- 赛事大厅：发现赛事。
- 我的赛事：组织和跟踪与我有关的赛事。
- 球搭子们：管理真实球友关系和临时球搭子。
- 我的：个人资产与设置入口。
- 我的战绩：看比赛结果，不承担赛事管理。
- 球搭子邀请记录：看球搭子关系邀请历史，不承担赛事邀请。

同一个主任务不要因为空状态、快捷方式或“方便”而在多个一级页面重复成为 Primary Action。

## 2. 卡片代表实体，动作代表行为

统一规则：赛事卡片进入赛事详情；真实球搭子卡片进入 TA 的档案；临时球搭子卡片进入临时球搭子管理/受限档案详情；战绩记录进入对应比赛/赛事上下文。“编辑 / 邀请 / 删除 / 报名 / 管理 / 代报名”等必须作为明确动作，不把点击整张实体卡片偷偷解释为“编辑”。

## 3. 展示优先，编辑按需

详情页默认用于阅读。编辑通过铅笔、文字按钮或明确入口进入。不要因为某对象“可编辑”就让其卡片直接打开表单；昵称头像与打球档案字段应在标题和入口上区分。

## 4. 空状态与参与事实

空状态包含：人话标题 + 一句解释 + 合理下一步，且不能改变页面职责。

“我参与的”必须按实际有效 Entry 中的 Player 参与事实判断：单打本人以及双打 Entry 中两名已关联真实用户的搭档都属于参与者；谁发起报名不是判断依据。仅接受赛事邀请、仅接受双打组队邀请但尚未形成有效 Entry，不应出现。无战绩意味着没有已完成比赛，不等于没有参加赛事；无球搭子与无临时 Player 是不同状态。

## 5. 邀请必须区分“关系”和“赛事”

球搭子关系邀请入口在“球搭子们”，历史在“我的 → 球搭子邀请记录”。赛事邀请入口和待处理状态归“我的赛事”；接受普通赛事邀请只表示接受邀请意向，不自动生成 Entry，界面必须继续引导完成报名。接受双打搭档邀请表示同意组队，不等于整个双打 Entry 已完成报名，最终报名动作必须有清晰归属。

## 6. 真实球搭子与临时球搭子

“我的球搭子”与“临时球搭子”必须分 Tab/分组。真实球搭子可查看对方允许展示的长期打球档案和历史战绩。临时球搭子由创建者管理，后台可以持续积累完整历史，但创建者前台只看到基础管理信息、是否已有历史的提示，以及“邀请 TA 加入球搭子”转化入口；临时球搭子成为用户并关联历史后，才把完整长期档案作为本人可使用的产品资产。

## 7. 赛事卡片信息与 V6 时间/级别规则

公开赛事移动端卡片支持快速决策，优先展示状态 + 类型/参赛建议级别、赛事名称、组织者、赛制/计分、日期时间、城市 + 场地、报名/名额 + 费用。参赛建议级别是区间型发现信息，不是硬报名门槛，前台不得重新出现单一“赛事级别”筛选概念。

公开/完整赛事卡显示安静的报名截止提示：>24小时显示具体时间，1–24小时显示约 N 小时，不足1小时显示即将截止，截止后显示已截止/已结束；不增加轮询。私有大厅脱敏卡不得显示截止时间、比赛时间或可反推时间的信息。

## 8. Primary Action 与移动端动作区规则

一页原则上一个最明显主操作。两个并列按钮只有在窄屏仍可读、可点且保留间距时才横排，否则纵向堆叠；三个及以上动作禁止连续大按钮矩阵。Primary、Secondary、详情入口必须有层级。所有动作布局至少检查 390px 及更窄移动端，不得出现按钮文字挤压、图标压文字、按钮互相覆盖、圆角相交或触控区重叠。

## 9. Loading / Cache / Refresh 体验

已有缓存时不应把页面重新清空成全屏 Loading。页面切换尽可能保留已知内容并后台刷新。同一 RPC/同一业务数据优先共用 cache key。稳定页面不固定 10/15 秒轮询，只有实时赛事/比分等场景可高频更新。用户主动刷新可强制请求最新数据；mutation 成功后精准 invalidate。

## 10. 权威身份与权限交互

身份/权限敏感页面不能仅依据可能过期的本地 Profile/cache 决定管理能力。赛事详情必须使用服务端赛事快照返回的 `viewer_role` 等权威事实决定 owner/invited/participant/viewer 对应入口；本地身份只辅助展示。旧 auth session 映射到 canonical Profile 的恢复场景不得导致合法组织者丢失管理入口。前端隐藏按钮不能替代服务端权限。

## 11. 报名截止交互

创建/编辑赛事按日期 → 开赛时间 → 最晚报名时间的顺序表达。默认截止为开赛前2小时；组织者只能设得更早。修改日期/开赛时间导致原截止不再合法时自动收紧，并明确告诉组织者“已自动调整”。截止是服务端权限边界；前端展示状态不能作为最终判断，更不得通过比较中文/英文展示文案决定可报名性。

## 12. 设置、隐私与语言

“我的 → 设置与隐私”承载真实设置。档案字段可见性只影响球搭子浏览，不隐藏合法赛事参与者应共享的名单、比分、赛果等赛事事实。赛事邀请与双打组队邀请开关独立，后端必须执行。

简体中文 / English 使用统一轻量 i18n。正式英文验收时核心流程必须完整可用，不允许同一核心任务页面出现影响理解的半翻译。业务状态和权限判断必须依赖结构化字段/helper，而不是展示文案。

## 13. 错误文案

用户错误提示结构：发生了什么 + 下一步能做什么。不要直接展示 Failed to fetch、JWT/auth session、SQL/RPC function、Postgres constraint、RLS 或 raw stack trace；技术错误可留日志。

## 14. 重构、死代码与数据字段全链路

页面迁移到新实现后删除旧整页实现。兼容代码必须明确兼容目的和退出条件。新增业务字段必须检查 DB schema → migration → RPC/repository → TypeScript type → create/edit form → list/detail response → UI display → filter → cache invalidation → 验收场景，禁止只在前端新增输入框或从其他字符串猜字段。

## 15. 设计一致性与部署前审计

新增页面前检查最相近现有页面，同语义操作复用组件/class；局部需求不得顺便重新定义全局按钮、卡片、颜色、导航或页面职责。

较大部署前完整审计至少覆盖 PRODUCT/INTERACTION/VISUAL/P0/PRD/CHANGELOG 一致性、核心 E2E 与状态机、migration 顺序和 clean replay、RPC/RLS/权限、cache/轮询/写后失效、错误/空状态、死代码/旧术语、HashRouter 分享深链、前后端字段一致性、390px 窄屏动作、构建状态以及平台限额与代码错误的区分。功能行为变化后文档必须同批同步；未同步即阻塞发布。
